# 社区"改机"归档的字节级补丁表（奥林巴斯解锁功能的真实形态）

> 日期：2026-10-22（第十四轮补全：6 个 RAR 归档全部解出）
> 数据源：xdel.ru `original/` 与 `patched/`、`patched_yandex/` 目录
> 方法：解包（ZIP 用标准库；RAR 用**完整版 7-Zip**，注意 `7zr.exe` 不含 RAR 解码器）
>       → `tools/oly_container.py` 解混淆 → 与对应**原版**固件逐字节差分
> 性质：**观察（静态）**。社区补丁的功能效果来自社区描述，本表只证明**字节差异**。

---

## 0. 为什么这张表重要

用户目标之一是"**解锁被锁住的功能**"。奥林巴斯没有公开过这些开关的位置，
但社区改机归档**直接把答案写在了字节里**：他们改的就是**门控判定的那几条指令**。
把这张表读懂，就等于拿到了"解锁"在固件层面的**可复用模板**。

本表同时是本项目差分管线的**正确性验证**：E-M5 II v4.1 补丁算出的
decoded 偏移 `0x3F2AD5 / 0x534866 / 0x53486C`，与 fishcu/oly_fw_analysis
独立记录的 `0x3f2ad5 / 0x534866 / 0x53486c` **逐字节吻合**。

### 1.1 三条新观察（本轮新增）

1. **模式 A 覆盖 9 个机型**（新增 E-M1 II v3.0、E-M1 v4.6、E-M10 II v1.3/v1.4、
   E-M10 III v1.2、E-PL9 v1.1）—— 它是**跨机型的通用门控**，是本表最有价值的发现。
2. **模式 A 有两个"比较常量变体"**：
   - A1 比较值 `0x14 / 0x03 / 0x08`（E-M1、E-M5、E-M10 III、E-PL9）
   - A2 比较值 `0x0C / 0x08 / 0x04`（E-M10 II、E-M1 v4.6）

3. **E-M10 II v1.3 / v1.4 只有 1 处补丁（只有模式 A，没有模式 B）**，
   PEN-F v3.1 则只有模式 C ⇒ **不同社区的"解锁"组合不同**，
   说明模式 A / B / C 是**三个相互独立的功能开关**。

## 2. 模式明细

### 模式 A —— 12 字节，"解除一串比较门控"（**9 个机型**）

两个常量变体，补丁后的字节序列**完全相同**：

```
stock A1 : 1c a0 06 c8  14 a0 03 c8  10 a0 08 c8
stock A2 : 1c a0 06 c8  0c a0 03 c8  08 a0 04 c8
patched  : fc cc 10 00  00 70 60 88  1c df 80 1c   (A1)
patched  : fc cc 10 00  00 70 60 88  1c df 80 08   (A2)
```

> 原序列可解读为「三组 `cmp imm8,d0` + `beq`」（`a0` = `cmp imm8,d0`，`c8` = `beq`，
> `14/03/08` 等为比较值），补丁序列则把它换成一组不同形态的指令。
> **补丁后序列的最后 1 字节随变体不同（`1c` / `08`）**，说明那是被改写的立即数/位移。

## 3. 偏移体系说明（重要）

本表给出**三种偏移**，互不等价：

| 体系 | 含义 | 用途 |
|---|---|---|
| `decoded` | 解混淆后块 0 内的偏移 | 反汇编定位（Ghidra / objdump 用这个） |
| `flash` | 运行时地址（块 0 装载地址 + decoded 偏移） | 与 fishcu 文档、各类 wiki 的地址一致 |
| `.BIN 文件偏移` | 原始固件文件内偏移（已计入 16 列置换） | 直接 `fc /b` 打补丁用；与社区文字配方格式一致 |

置换关系（来自 `tools/oly_container.py` 的 `DECODE_ORDER`）：
`raw = block_payload_start + DECODE_ORDER[off % 16] + 16 * (off // 16)`。

## 4. 对本项目目标的意义

1. **"解锁功能"的字节形态已知**：社区改机就是改块 0 里 2~14 字节的门控判定。
   本项目若要解锁 E-P5 的某个功能，需要做的是**同一种手术**：
   找到对应判定 → 改 2~12 字节 → 重算 sum32 → 重新打包 → 刷机。
2. **模式 A 在 9 个机型上复现** ⇒ 它是**跨机型的通用判定**（很可能是
   "此功能在本机型/本地区是否支持"一类的门控）。
   ⇒ **在 E-P5 上定位同一段判定的可行性很高**：
   用 `tools/find_opcode_pattern.py` 以模式 A 的指令序列特征
   （`1c a0 ?? c8 ?? a0 ?? c8 ?? a0 ?? c8`）在 E-P5 块 0 里搜索。
3. **模式 B / C 在多个机型上复现** ⇒ 同样对应**跨机型通用的判定**。
4. 这些补丁**全部不在块 1/2/3**，因此"改块 0 的代码 + 重算校验和"是完整可行的路径。

### 4.1 E-P5 上的初次搜索结果（本轮）

在 **E-P5 v1.8 块 0**（`0x402C0000`，15,728,576 B）里：

- 模式 A 的**完整 12 字节序列（含比较常量）命中 0 处**；
- 放宽到**结构型** `1c a0 ?? c8 ?? a0 ?? c8 ?? a0 ?? c8` 仍**命中 0 处**；
- 但搜到 **7 处 `1c a0 06 c8`**（`cmp 6,d0` + `beq`），
  其中 4 处构成**连续 case 的 switch 链**（比较值 3,4,5,6,7），例如：
  - `rt 0x404D583D`：前 `1c a0 03 c8 1c a0 04 c8 1c a0 05 c8` + 命中 `1c a0 06 c8` + 后 `1c a0 07 c8`
  - `rt 0x404B8AC7`：前 `1c a0 03 c8 1c a0 04 c8 1c a0 05 c8` + 命中 `1c a0 06 c8` + 后 `1c ca ...`
  - `rt 0x4043C411`：前 `1c a0 04 c8 18 a0 02 c8 14 a0 03 c8 10 a0 00 c8` + 命中 `1c a0 06 c8`
  - `rt 0x4051B16C`：命中 `1c a0 06 c8` + 后 `1c a0 0a c8 26 a0 0b c8 30 a0 1b c8`

⇒ **推断**：E-P5 的该段代码与社区所改机型**不是同一份源码**（case 集合与顺序都不同），
所以**字节级特征匹配在此不适用**；需要在 E-P5 侧改用**语义定位**
（反编译出这些 switch，看它们分派的是哪一类模式值）。
**这一条尚未完成，是下一步。**
