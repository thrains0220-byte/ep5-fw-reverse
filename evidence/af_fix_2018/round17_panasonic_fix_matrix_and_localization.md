## 3. 镜头 ID 比较链：修复前后**完全一致** ⇒ 证伪上一轮推断

### 3.1 复现方法【观察】

`tools/lens_chain_scan.py`（全 disp 0..63 扫描「两字节前缀比较链」）：

| 固件 | 窗口（运行地址） | 高字节常量 | 次字节常量 |
|---|---|---|---|
| E-PM2 **v1.5（修复前）** | `0x403D3D3E..0x403D3E3E` | `C1 C0 81` | `80 00 F1 E1 80 F1 E3 F1 28` |
| E-PM2 **v1.6（修复后）** | `0x403D3D3E..0x403D3E3E` | `C1 C0 81` | `80 00 F1 E1 80 F1 E3 F1 28` |
| E-P5 **v1.8（目标）** | `0x403B7975..0x403B7A75` | `C1 C0 81` | `39 80 00 F1 E1 80 F1 E3 F1 28 39` |

### 3.2 结论【观察 + 推断】

- 两版 E-PM2 的镜头 ID 白名单链**逐项相同**：高字节 `{C1, C0, 0x81}`，
  次字节 `{0x80, 0x00, 0xF1, 0xE1, 0x80, 0xF1, 0xE3, 0xF1, 0x28}`。
- ⇒ **修复没有新增、删除或修改任何镜头 ID 白名单项。**
- ⇒ 【推断】上一轮报告 §5.5 的「候选补丁字节 = `0xC0F1` / `0xC0E1`」**被证伪**：
  这两个比较项在**修复前就已存在**，不可能是修复引入的补丁字节。
- ⇒ 【推断】修复**不是**「把松下镜头加进 ID 白名单」这种形态。
  修复更可能是**改变了对既有镜头 ID 的处理行为**（参数选择 / 分支条件 / 调用时序）。

## 5. 代码块差异的性质：绝大部分是地址重定位【观察】

### 5.1 指令级字段分类（E-PM2 v1.5 → v1.6，objdump 指令边界，非字节扫描）

差异字节 2,969,985（含 2,969,352 代码字节）：

| 类别 | 字节 | 占比 |
|---|---|---|
| 2 字节指令的助记符/立即数字段 | 1,113,865 | 48% |
| `mov` 立即数 | 256,965 | 11% |
| `call` 相对转移偏移 | 248,683 | 10% |
| 6 字节 `fc` 立即数（32 位绝对地址 / 常量） | 194,336 | 8% |
| `movhu` / `movbu` | 119,879 / 102,371 | 5% / 4% |
| 其余转移（beq/bne/bra/jmp/…） | ~140,000 | 6% |
| **真正落在非指令区（数据表 / 字符串）** | **26,918** | **1%** |

### 5.2 区域级「搬走 vs 真改」判定

把 349,195 个差异区间按距离 ≤64 B 聚成 8,769 个**变化区**，逐区做 64 B 精确匹配：

| 判定 | 区数 | 覆盖差异字节 |
|---|---|---|
| 被搬走（可精确匹配到 B 的别处） | 205 | 413,391 |
| 其余（就地字段改写 / 局部小位移 / 数据表增删） | 8,564 | 2,555,961 |

搬移位移分布主要为 `+16`（124 KB）、`+684`（232 KB）、`+648`（34 KB）、`+8`、`+4`、`-660`、
`-2344` … ⇒ **代码确实整体搬移过**。

### 5.3 唯一「无对应内容」的大区（已查明为布局位移，不是语义改动）

`A 0x004E3B12..0x004F1BB2`（57,504 B）在 B 中找不到对应内容。逐字节差分模式：

- 差异字节在区内偏移上的分布：mod 4 = {0:1825, 1:1906, 2:1840, 3:1771} ⇒ 均匀分布，**不是**单字段。
- 差异值对：`0xD2→0xD3` ×400、`0x04→0x14` ×82、`0x05→0x15` ×81、`0x06→0x16` ×53 …

objdump 反汇编（运行地址 `0x407A3B00` 附近）：

```
A(v1.5):  fc 82 05 d2 5c 60    movbu  d0,(0x605cd205)
          fc 82 06 d2 5c 60    movbu  d0,(0x605cd206)
B(v1.6):  fc 82 15 d2 5c 60    movbu  d0,(0x605cd215)
          fc 82 16 d2 5c 60    movbu  d0,(0x605cd216)
```

⇒ 指令语义**完全相同**，只是**目标 RAM 地址整体 +0x10**（RAM 变量布局位移）。
写入的**值序列也完全相同**（1, 76, 252, 139, 88, 117 …）。

【推断】代码块差异 ≈ **地址重定位 + 少量数据表增删**，真正的语义改动被淹没在噪声里；
必须靠 §4 的字符串签名与 §3 的链比对来锁定，而不是靠字节差分。

| 03 0x010E（262,080 B） | **完全相同** |
| 04 0x0102（9,437,120 B） | **完全相同** |

区域级分析给出的语义改动样例：

- 新增调试串 `seek_last_wait (event = …`
- 新增数据表（`0x0018FDA0`：`10100011 22334455 66778899 aabbccdd eeff…`）
- `0x0104E8C0..0x0107764C`（167 KB）表内容整体替换
- `0x00E54540..0x00E9F590`（307 KB）由 `7754c660…` 变为 `0255c660…` 重复模式

【推断】一次**真实功能新增**在本平台上的指纹是：
① 新增标识符串；② 新增/替换数据表；③ 代码块差异。
**松下修复的指纹只有 ①（且是"移除"）**，没有 ② ⇒
【推断】松下修复**不引入任何新参数表**，只改既有 `fcs_lens_mfts` 代码路径。

## 7. 官方服务器协议：OMSRV 接口现状【观察】

### 7.1 接口与请求格式（实测）

```
POST https://fw01.om-digitalsolutions.net/ww_inform/fcache.do
Content-Type: text/xml; Charset=UTF-8
User-Agent: Olympus
```

请求体（`firmware_demand` XML）关键字段：

| 字段 | 值 | 说明 |
|---|---|---|
| `<hard_code>` | `OLYE` + **机型码前 3 位** + **9 个 `0`**（共 16 字符） | 例：`OLYE108000000000` → 机型 1080。**长度必须与官方样本一致**，写成 4 位机型码会得到退化响应 |
| `<firmware_version>` | 机身当前版本（4 位十六进制，如 `00001000`） | |
| `<mac_address>` / `<time>` | 沿用官方样本 `00-00-00-00-80-D6` / `20261022215527` | 换成随机值会导致响应退化（只回显版本号、无文件信息）。服务器会**覆盖**响应里的 `<time>` 为服务器当前时间 |
| `<version>` | `00005000`（更新器自身版本） | |

响应体 `<firmware_info>` 含
`model_name / model_id / version / file_name / file_size / up_date / detail_url / url`，
其中 `<url>` 是**带签名的直链**：

```
https://dl01.om-digitalsolutions.net/OMDS/FIRMWARES/0001/1080/OLY_E_108_1800_0000_0000.BIN
  ?Expires=…&Signature=…&Key-Pair-Id=KXX19K1PXVDZ7
```

签名有效期约 **3 分钟**（`Expires` 字段），大文件需断点续传。

### 7.2 行为

| 请求 `firmware_version` | 响应 |
|---|---|
| `00001000` / `00001200` / `00001300` / `00001700` | 返回**最新版** + 签名直链 |
| `00001800`（= 最新） | 返回 `version=1800` 但 `file_name`/`file_size`/`url` **为空**（无需更新） |

参数扫描（`firmup_mode` 0–3、`type` 0000–0002、`hard_code` 变体、`version` 变体、
端点 `fcache.do`/`firmware2.do`/`firmware.do`/`fcache2.do`）**未发现任何可返回历史版本的组合**。

### 7.2b 三重校验：OMSRV 下载 ≡ MANIFEST ≡ 仓库 blob【观察】

用 OMSRV 签名直链下载两个仓库里缺失的 2018-12-18 修复版本，与仓库既有哈希比对：

| 固件 | OMSRV 下载件 SHA-256 | MANIFEST 期望 | 仓库 git blob |
|---|---|---|---|
| E-PL6 v1.4 | `f7b76ac82d545148bfc1c00bc165fb855b2e7d044dcaae1033601496e1bd116f` | 同 | 同 |
| E-M10 v1.4 | `84d81b2dbd80ea2e94ec70e35acbba0e3193ccee8b51db14976fd0d9c4e3590c` | 同 | 同 |

⇒ **官方服务器、仓库清单、仓库实体三者完全一致**；
⇒ 也说明 `firmware/pre_fix/` 里那两个 0 字节文件**只是本地工作区残留，仓库本体从未损坏**
（`git cat-file` 显示 blob 完整；`git checkout` 被 sparse-checkout 拦，改用 `git show` 取出即可）。


### 7.3 为什么旧版本取不到

| 尝试 | 结果 |
|---|---|
| 未签名直链 `…/0001/1080/OLY_E_108_1700_…BIN` | HTTP 403，CloudFront `MissingKey` |
| 把 1800 的签名换到 1700 文件名 | HTTP 403（签名绑定路径） |
| 把 1800 的签名换到别的机型目录 | HTTP 403 |
| `…/OLYMPUS_MASTER/FIRMWARES/…`（旧站路径） | 连接被拒（站点已下线） |
| 逐个 `index01a..18a.html`（1080/1150/1200/1250/1300/1340/1370/1390/1180） | 全部 200，但**无任何 `.BIN` 链接**（纯发布说明页） |
| Wayback CDX（OMDS 路径） | 每个机型**只有最新版** |
| xdel.ru | 域名被 DNS 解析到 sinkhole `198.18.0.13`，不可达 |

【推断】**历史版本固件在公网上已不可得**；
⇒ 必须靠 `pre_fix/` 里已有的「修复前」样本做差分（本轮 §2 的做法），
   **不能再等新下载**。

## 8. 方法论修正（本轮踩到的坑）

| # | 问题 | 症状 | 修法 |
|---|---|---|---|
| 1 | `diff_field_classify.py` 用 objdump **绝对地址**当文件偏移 | 100% 差异字节被判成"数据区" | objdump `--adjust-vma` 后的地址须减 base；已加 pickle 缓存 |
| 2 | 按**下标**配对两条指令流 | 指令数 Δ=+260 后整体漂移，产出 3,761,972 条假"助记符不同" | 改为**按偏移配对**；再用区域级精确匹配补齐搬移 |
| 3 | GNU diff 3.8 **不接受 `--no-color`** | `rc=2`、**静默输出 0 字节**，误判为"无差异" | 改用 `--color=never` |
| 4 | `decode_fw4.sh` 找 `manifest.json` 的路径层级错 | 12 个已解码固件被误报"容器解码失败" | 改为 `$out/decoded/manifest.json` |

| 6 | `diff_field_classify.py` 缓存文件名用 `basename` | 两版同名（`00_0100_40300020.decoded.bin`）互相覆盖缓存 | 缓存名加路径 SHA-1 前 10 位 |
