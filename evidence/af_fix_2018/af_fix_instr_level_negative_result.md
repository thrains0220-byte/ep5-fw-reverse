# 2018-12-18 松下镜头 AF 修复 —— 指令级差分与「修复不在 .BIN 代码内」的结论

> 日期：2026-10-23
> 结论性质：**观察（静态）**。不含执行 / 刷机证据。
> 覆盖基线：E-PM2 v1.5.0.1（修复前）→ v1.6.0.0（修复后）、E-M5 v2.2（修复前）→ v2.3（修复后）
> 目标机型坐标：E-P5 v1.8（块 0，基址 `0x402C0000`）

---

## 0. 一句话结论

**2018-12-18 的松下镜头 AF 修复，不在固件 `.BIN` 的代码块里。**
在 E-PM2 与 E-M5 两个机型的「修复前 → 修复后」同机型差分里，
镜头/AF 代码区**逐条指令完全一致**（零插入、零删除），
唯一的差别是**所有 mask ROM 地址常量整体位移**（E-PM2 `+0x2AC`、E-M5 `+0x2C0`）
⇒ **机身 mask ROM 映像在修复版里被扩充了**，修复的实体内容在 ROM 映像中，而不在 `.BIN` 中。

## 4. 观察 3（核心）：镜头/AF 代码区在修复前后**逐条指令相同**

### 4.1 方法

以「镜头 ID 两字节前缀比较链」为**锚点**——该链在两个版本里**地址完全不动**：

| 机型 | 链窗口（修复前 = 修复后） |
|---|---|
| E-PM2 | `0x403D3D1E..0x403D3E0E` |
| E-M5 | `0x904B26CC..0x904B27BC` |
| E-P5 1.8 | `0x403B7965..0x403B7A30` |

工具：`tools/instr_diff.py`（GNU objdump `--target=mn10300-elf --insn-width=16`
→ 逐地址解析 `(助记符, 操作数)` → 同地址比对）。

### 4.2 E-PM2 v1.5.0.1 → v1.6.0.0，窗口 `0x40300000..0x40480000`（1.5 MB）

```
A 指令 645,858   B 指令 645,858
操作数不同 8,429   仅 A 有 0   仅 B 有 0        ← 零插入、零删除
```

操作数差异按差值分类：

| 差值 | 条数 | 含义 |
|---|---|---|
| `+0x2AC` | 7,608 | **mask ROM 映像整体位移** |
| `0` | 529 | 调用目标 / 寄存器重命名等链接噪声 |
| `+0x280` | 1 | 同上区段的不同插入点 |
| 其余 292 条 | 292 | 全部是 `mov (0x7Exxxxxx)` 形式，差值同样为 `+0x2AC` |

**⇒ 这 1.5 MB（镜头 ID 链 + 镜头子系统 + 相邻 AF 代码）里没有任何语义改动。**

### 4.3 E-M5 v2.2 → v2.3，窗口 `0x90460000..0x904E8000`（576 KB）

```
A 指令 217,190   B 指令 217,190
操作数不同 6,016   仅 A 有 0   仅 B 有 0
差值分布：+0x2C0 × 4,363   0 × 1,469   其余同为 +0x2C0
```

**⇒ 跨机型复核一致：同样零语义改动。**

### 4.3.1 全块对照：为什么强结论必须限定在「对齐窗口」内

把同一套指令级差分跑满 **E-PM2 块 0 全部 14,155,712 B**：

```
A 指令 7,207,257   B 指令 7,207,517
操作数不同 922,789   仅 A 有 790,644   仅 B 有 790,904
```

⇒ **全块范围内线性反汇编的指令边界会漂移**（79 万处只剩单侧），
因为整体重编译把代码搬了位置，边界不再一一对应。

⇒ 因此**「零插入零删除」只在地址不动的对齐窗口内成立**；
本报告的强结论（§4.2 / §4.3）**明确限定**在
E-PM2 `0x40300000..0x40480000` 与 E-M5 `0x90460000..0x904E8000` 两个窗口内，
不外推到全块。全块范围内「镜头/AF 代码无语义改动」是**未知**，不是已证事实。

### 4.4 镜头 ID 链函数本身：唯一差异是一条 ROM 常量

E-PM2 v1.5.0.1 `0x403D3DD4` 与 v1.6.0.0 `0x403D3DD4`：

```
修复前:  fc dc fc 1b 74 7e     mov 0x7E741BFC,a0
修复后:  fc dc a8 1e 74 7e     mov 0x7E741EA8,a0      ← 差 +0x2AC
```

E-M5 v2.2 `0x904B2584` 与 v2.3 `0x904B2784`：

```
修复前:  fc dc a6 66 87 7e     mov 0x7E8766A6,a0
修复后:  fc dc 68 69 87 7e     mov 0x7E876968,a0      ← 差 +0x2C0
```

该指令位于镜头 ID 组装序列中：

```
f8 42 0e      movbu (14,a2),d0      ; 记录 +14（厂商码）
f8 4a 0f      movbu (15,a2),d2      ; 记录 +15（型号）
90 10         mov 16,a0
f1 78         add a2,a0
f0 44         movbu (a0),d1         ; 记录 +16
f8 4c 01      movbu (1,a0),d3       ; 记录 +17
fc dc XX XX   mov <mask ROM 地址>,a0   ← 唯一被改动的常量
f8 c0 18      asl 24,d0
f8 c2 10      asl 16,d2
f2 18         or d2,d0
f8 c1 08      asl 8,d1
f2 14         or d1,d0
f2 1c         or d3,d0
dd 86 17      call <函数>,[d2,a2],40
```

⇒ 这是**「用哪一组 ROM 参数」的指针**，它的位移等于 ROM 映像的位移，
本身不是补丁。

## 5. 观察 4：mask ROM 映像在修复版里**被扩充**

对全块 0 扫描所有落在 `0x7D000000..0x7FFFFFFF` 的 32 位常量
（`tools/rom_ptr_diff.py`），在「唯一字符串锚点对齐」后统计位移分布：

| 机型对 | 主位移 | 次位移 | 解释 |
|---|---|---|---|
| E-PM2 v1.5.0.1 → v1.6.0.0 | `+0x2AC` × 11,362 | `+0x288` × 7,345 | ROM 映像有**两个插入点** |
| E-M5 v2.2 → v2.3 | `+0x2C0` × 12,285 | `+0x298` × 8,125 | 同上 |

⇒ ROM 映像在修复版里**变大了**（两个区段分别后移 0x2AC/0x288 与 0x2C0/0x298）。

**⇒ 推断（高置信）**：2018-12-18 的松下镜头 AF 修复，
实体内容是**机身 mask ROM 映像里新增/改写的数据**（很可能是 H-ES200 / H-ES50200
的 AF 调校参数或镜头识别所需的附加数据），
而 `.BIN` 的代码块只因引用偏移变化而被重新链接。

**⇒ 推论（对项目既有结论的修正）**
项目此前在 `evidence/af_fix_2018/lens_info_af_layout.md` §2 写的是
「每镜头 AF 调校参数在机身 mask ROM ⇒ **固件补丁无法改写**」。
按本轮证据，更准确的表述是：

> 每镜头 AF 调校参数在**机身 mask ROM**（不在 `.BIN` 的任何块里 ——
> 块 1/2/3/4 在修复前后逐字节相同，而 `.BIN` 里没有一块的运行时地址覆盖
> `0x7Exxxxxx`）。
> 因此**在 `.BIN` 层面无法改写 AF 参数本体**；
> 但**机身 ROM 映像本身在官方修复版里被改写过**（本轮实测），
> 所以「能否改」取决于 ROM 映像的交付方式（是否随固件包下发），这仍是**未知**。

## 5.1 P0 追问：mask ROM 映像到底在哪里？——**四项独立检验，都说「不在 `.BIN` 里」**

| # | 检验 | 结果 |
|---|---|---|
| 1 | `.BIN` 容器里有无隐藏数据 | E-PM2 v1.6 五个块的 payload 合计 43,319,040 B + 5×64 B 块头尾 = 43,319,360 B = `.BIN` 全长 ⇒ **无隐藏块** |
| 2 | 有无某块的运行时地址覆盖 `0x7Exxxxxx` | E-P5 1.8 四块地址：`0x402C0000` / `0x427C0020` / `0x43DA0020` / `0x44000020`；E-M5：`0x902C0000` / `0x40060000` / `0x92E40000` / `0x94440000` / `0x946A0000` ⇒ **无一覆盖** |
| 3 | 块 0 里有没有「位移后整段相同」的 ROM 映像 | 用 `+0x2AC` / `+0x2C0` 做位移扫描找最长匹配段，**并剔除单一填充值**：最长「有意义」段只有 **255,778 B**（E-PM2 `0x405E95BE`，正是镜头子系统数据区），远小于 ROM 密集区 ≈ 13.4 MB ⇒ **ROM 映像不在块 0** |
| 4 | 官方更新包/服务器是否另发一个 ROM 文件 | Win64 更新器 `.rsrc` 里唯一的巨型资源是 **15,996,237 B 的 MSCF（Microsoft Cabinet）**，`7z l` 解出的是 2016 年的通用安装包（`setup_FWT.exe` / `FwUpTool.msi` / `OlyGlossaries.dll` / 驱动 / vcredist），**无 ROM、无第二份固件**；macOS 包只有 2.4 MB；官方 MSRV 服务器对每个型号**只返回一个文件**（`firmware/notes/omsrv/rep_E108.xml`：`file_name=OLY_E_108_1800_0000_0000.BIN`，`file_size=44826624`，单个 `<url>`）⇒ **更新链路里没有 ROM 映像** |

**⇒ 结论（观察级）**：机身 `0x7Exxxxxx` 区域的内容**不由 `.BIN` 承载，也不随固件更新下发**。
它随修复版发生了布局变化（`+0x2AC` / `+0x298` 等），
说明官方在发布这次修复时**同时更新了机身 ROM**，
但那部分**不在这份固件包里**。

**⇒ 对本项目目标的直接影响（推断级，高置信）**：
> 「在 `.BIN` 里找到松下镜头 AF 修复的补丁字节」这个目标，
> **很可能不存在可交付物** —— 因为修复实体不在 `.BIN` 里。
> `.BIN` 里能看到的只是「因 ROM 布局变化而被重新链接的引用偏移」。

**这修正了项目此前的框架性假设**：
原 `lens_info_af_layout.md` §2 的结论「参数在 mask ROM ⇒ 固件补丁无法改写」
方向是对的，但**理由需要升级**：
不只是「改不了」，而是「**连官方自己的 `.BIN` 都不承载这部分数据**」。

## 10. 方法论补充（建议写进 `RE_METHOD_PLAYBOOK.md`）

1. **先找「地址不动」的功能锚点**。
   本轮的关键突破不是差分算法，而是发现「镜头 ID 比较链在两个版本里地址完全相同」。
   地址不动的代码段 ⇒ 指令边界天然对齐 ⇒ 可以做**逐条指令比对**，
   把「常量改写」与「链接噪声」彻底分开（字节级差分做不到）。

2. **指令级差分 + 常量位移分类**是判定「语义是否变化」的最省事办法：
   把所有操作数差值统计成直方图，**主位移 = 布局变化**，
   剩下的才是语义改动。本轮 8,429 条差异里 8,428 条属于布局/噪声。

3. **区分「同一处常量」与「同一处代码」**：
   本轮差点把 `mov <mask ROM 地址>` 的位移当成补丁。
   判据是：**该常量的位移是否等于全块 ROM 指针的主位移**。
   等于 ⇒ 布局噪声；不等于 ⇒ 语义改动。

4. **跨机型交叉验证**：同一修复在 E-M5 与 E-PM2 上必然产生**同形态**的差分
   （本轮：同样的零插入零删除、同样的「只有 ROM 位移」）。
   两个机型给出一致结论时，才允许下强结论。
