# 菜单描述符的「类型码」机制 —— 「录像艺术滤镜只 4 项」的可补丁落点

> 日期：2026-10-22（第十四轮续）
> 基线：E-P5 v1.8 块 0（`decoded/00_0100_402c0020.decoded.bin`，基址 `0x402C0000`）
> 方法：Ghidra 12.1.4 + MN10300 SLEIGH 模块，反编译器伪代码为证据。
> 性质：**观察（静态）**。

---

## 0. 一句话结论

> **菜单项清单本身在机身 mask ROM（不可改写），
> 但「用哪一份清单」由块 0 里的一个字节决定 ——
> 即 `mode_state + 0x6B` 的「类型码」。**
>
> ⇒ **「解锁录像艺术滤镜」= 让录像路径写入与照片路径相同的类型码，
> 或在描述符选择函数里把录像那一档改成照片那档的 mask ROM 地址。**
> 这是 **1~4 字节的块 0 补丁**，与社区改机同一种手术。

这一条把第十四轮前半段的结论（「菜单清单在 mask ROM ⇒ 不可改」）**升级为可操作**。

> ⚠️ **诚实边界**：`FUN_403E7E94` **是否就是「艺术滤镜菜单组」目前只是推断**
> （依据是 case 集合 {2,3,4,5,6} 与「照片 10 项 / 录像 4 项」的形状吻合）。
> **未证实**，需要 mask ROM 里那几份描述符的实际内容。
> 本文件描述的**机制**（类型码 → mask ROM 描述符）不依赖这一认定。

## 2. 类型码解码器 `FUN_403ED4B4`

块 0 `rt 0x403ED4B4`（flash `0x403ED4B4`）：

```c
undefined4 FUN_403ed4b4(uint param_1)
{
  uint uVar1 = param_1 & 7;
  if (uVar1 == 0) {
    param_1 &= 0xe0;
    if (param_1 == 0)    return 0;
    if (param_1 == 0x20) return 1;
    if (param_1 == 0x80) return 4;
    if (param_1 == 0xa0) return 5;
    if (param_1 == 0xc0) return 6;
  }
  else if ((uVar1 == 2) || (uVar1 == 3)) {
    if ((param_1 & 0xe0) == 0x20) return 1;
  }
  else {
    if ((uVar1 == 4) || (uVar1 == 5)) return 2;
    if (uVar1 == 7) return 3;
  }
  return 0;
}
```

**观察**：这是一个**位域解码器** ——
原始字节的 bit0–2 是「子类型」，bit5–7 是「组」，解码后得到**规范类型码 0..6**。

| 规范码 | 触发条件（原始字节） |
|---|---|
| 0 | low3=0 且 group=0x00/0x40；low3=1/6；low3=2/3 且 group≠0x20 |
| 1 | low3=0 且 group=0x20；或 low3∈{2,3} 且 group=0x20 |
| 2 | low3∈{4,5} |
| 3 | low3=7 |
| 4 | low3=0 且 group=0x80 |
| 5 | low3=0 且 group=0xA0 |
| 6 | low3=0 且 group=0xC0 |

## 3. 描述符选择函数族 —— 6 个平行函数

块 0 `0x403E5529`–`0x403E7E94` 有一族**结构完全平行**的函数，

| `FUN_403E5529` | `0x7E477734` | ←同码2 | ←同码2 | `0x7E47798C` | `0x7E477BE4` | `0x7E477E3C` |
| `FUN_403E7B1B` | `0x7E452B30` | `0x7E452B40` | ←同码2 | `0x7E452B48` | `0x7E452B50` | `0x7E452B58` |
| `FUN_403E7B79` | `0x7E452B34` | `0x7E452B44` | ←同码2 | `0x7E452B4C` | `0x7E452B54` | `0x7E452B5C` |

| `FUN_403E7E94` | `0x7E452BDC` | `0x7E452BE4` | ←同码2 | `0x7E452BEC` | `0x7E452BF4` | `0x7E452BFC` |

**观察**：
1. 每个函数对应**一组 UI 资源**（菜单组）。
2. 每个函数的 5~6 个返回值在 mask ROM 里**相隔 4 字节**（`0x7E452Bxx` 家族）
   或 8 字节（`0x7E477xxx` 家族）—— 说明 mask ROM 里排布着**等长的描述符记录**。

> ⚠️ **诚实边界**：`FUN_403E7E94` **是否就是「艺术滤镜菜单组」目前只是推断**
> （依据是它的 case 集合 {2,3,4,5,6} 与「照片 10 项 / 录像 4 项」的形状吻合，
> 以及它落在 `0x7E452Bxx` 这一组连续描述符里）。
> **未证实**。要证实需要 mask ROM 里这 6 份描述符的**实际内容**
> （即里面列的资源 ID 是否含 `A03F`–`A048`）—— 需实机 dump。
> 本文件其余部分描述的**机制**（类型码 → 描述符）不依赖这一认定。

`FUN_403E7E94` 伪代码：


⇒ **类型码 2 与 3 共用同一个描述符**（`0x7E452BE4`），

## 4. ⇒ 解锁方案（推断，待实机验证）

### 4.0 原始字节 → 规范码 → 描述符（**已按位域解码器重算，修正上一版**）

**关键**：`obj+0x6B` 存的是**原始位域字节**，`FUN_403ED4B4` 把它解成规范码。
逐个取值重算（`low3 = raw & 7`，`group = raw & 0xE0`）：

| 原始字节 | 规范码 | 说明 |
|---|---|---|
| `0` / `1` / `2` / `3` / `6` | **0** | `group` 不在 {0x20,0x80,0xA0,0xC0} 且 `low3` 不在 {4,5,7} ⇒ 落回 0 |
| `0x20` / `0x22` / `0x23` | 1 | `group == 0x20` |
| `4` / `5` | **2** | `low3 ∈ {4,5}` |
| `7` | 3 | `low3 == 7` |
| `0x80` | 4 | `group == 0x80` |
| `0xA0` | 5 | |
| `0xC0` | 6 | |

⇒ **`FUN_403E7E94` 实际只用两张描述符**：

| 规范码 | 返回的 mask ROM 描述符 |
|---|---|
| 0（默认）/ 1 | **`0x7E452BDC`** |
| 2 / 3 | **`0x7E452BE4`** |

### 4.0c ★ 单字节补丁位置（具体）

`FUN_405731F7`（`rt 0x405731F7`）末尾：

```c
*(undefined1 *)(param_1[0x18] + 0x6b) = 4;      /* ← ★ 这条立即数就是补丁点 */
```

同一函数里还有：

```c
*(undefined1 *)(param_2 + 0x69) = *(undefined1 *)(uVar3 + 0x7e4f1bdc);   /* +0x69 ← mask ROM */
```

⇒ **改法**：把 `= 4` 改成 `= 0`（或 `= 3`，两者都解码成规范码 0）
⇒ **UI 就会改用 `0x7E452BDC` 那份描述符。**

> **强烈推断**（未证实）：既然照片艺术菜单有 10 项、录像艺术菜单只有 4 项，
> 而两份描述符分别对应规范码 0 与 2，
> 那么 **`FUN_405731F7` 就是「短菜单」那一侧（很可能是录像侧）**，
> 把它改成 `= 0` 即可让该侧换用 10 项的那份描述符。
>
> **证伪/证实方法**：实机刷入后进录像艺术滤镜菜单，看条目数是否由 4 变 10。
> **或者**：读 mask ROM `0x7E452BDC` / `0x7E452BE4` 两份描述符里的资源 ID 列表，
> 确认哪一份含 `A03F`–`A048`（10 项）。

### 4.2 方案 2（细）：改描述符选择函数 ★备选

`FUN_403E7E94` 里把「短菜单」那一档的返回值改成另一张：

### 4.3 方案 1（粗）：改类型码写入

改 `FUN_405D2DBA` / `FUN_405D30DC` / `FUN_405D458E` 里写 `+0x6B` 的那个立即数。
**风险**：会同时影响其它 UI 菜单组（同一字节还被别的描述符族用）。

### 4.4 方案 3（社区同型）：改分派器

参照社区模式 A，把整个分派换成常量。
**在 E-P5 上不适用**（字节特征不匹配，见 `unlock_semantics.md` §4）。


> 把录像路径的赋值改成照片的值 —— **同样是 1 字节**，但作用面比改 `+0x6B` 更聚焦。

## 6. 拍摄状态数组（照片/录像开关本体）

`FUN_405D0FED()` / `FUN_405D1013()` 读的 `sRam602AE77A` 属于一个
**6 × u16 的拍摄状态参数组** `@0x602AE778`：

| 全局 | 数组下标 | 说明 |
|---|---|---|
| `uRam602AE778` | 0 | |
| `uRam602AE77A` | 1 | **照片/录像判据**（`FUN_405D0FED` 读它） |
| `uRam602AE77C` | 2 | |
| `uRam602AE77E` | 3 | |
| `uRam602AE780` | 4 | |
| `uRam602AE782` | 5 | |

### 6.1 判据表

```c
undefined4 FUN_405d0fed(void) {
  if ((sRam602ae77a == 100) || (sRam602ae77a == 0x66) || (sRam602ae77a == 0x68)) return 2;
  if (sRam602ae77a == 2) return 1;
  return 0;
}
bool FUN_405d1013(void) { return sRam602ae77a == 0x68; }
```

| `uRam602AE77A` | `FUN_405D0FED()` 返回 | 含义 |
|---|---|---|
| `0` | 0 | 未设定（默认） |
| `2` | **1** | **照片侧** |
| `100` / `102` / `104` | **2** | **录像侧** |

> **判据的独立佐证**（艺术子系统的判据，与上表同向）：
> `FUN_40788A6C`（`rt 0x40788A6C`）里
> ```c
> if (**(int **)(param_1 + 4) == 0x20000000) { ... }   /* ← 录像侧 */
> else { if (**(int **)(param_1 + 4) != 1) return; ... } /* ← 照片侧 */
> ```
> 而 `FUN_405D2BD0` 正是「`FUN_405D0FED() == 2` 时置 `0x20000000`」，
> ⇒ **`FUN_405D0FED() == 2` ⇔ 录像侧**，
> ⇒ `uRam602AE77A ∈ {100,102,104}` = 录像侧、`== 2` = 照片侧。

### 6.2 写入点（唯一）

`0x602AE77A` 全块只有 **1 处写**（其余 7 处全是读）：

```c
short FUN_405d0898(undefined2 *param_1) {     /* rt 0x405D0898 */
  short sVar1 = -0x63fe;
  if (param_1 != (undefined2 *)0x0) {
    sVar1 = FUN_405d12d9();
    if (sVar1 == 0) {
      uRam602ae778 = *param_1;
      uRam602ae77a = param_1[1];       /* ←★ 照片/录像开关的唯一切换点 */
      uRam602ae77c = param_1[2];
      uRam602ae77e = param_1[3];
      uRam602ae780 = param_1[4];
      uRam602ae782 = param_1[5];
    }
  }
  return sVar1;
}
```

默认值由 `FUN_405D092D()` 设定：`[0]=0, [1]=0, [2]=1, [3]=0, [4]=0, [5]=0`。

**调用链（已逐级确认）**：

```
FUN_405D363B                       (rt 0x405D363B)   ← 唯一直接调用者
  └─ CALL FUN_405CFD74
       FUN_405CFD74(param_1)        (rt 0x405CFD74)
         └─ FUN_405D0898(param_1 + 4)     ← 把 6×u16 拷进全局
              FUN_405D0898            (rt 0x405D0898)
                └─ uRam602AE77A = param_1[1]   ★★ 照片/录像开关本体
```

> **⇒ 上游开关**：`FUN_405D363B` 传入的 6×u16 块的第 2 个元素（`param_1[1]`）
> 就是照片/录像判据 —— 录像侧填 `2`，照片侧填 `100`/`102`/`104`。
> **这是比改 `+0x6B` 更上游的开关**，但作用面是整个拍摄状态，
> 会同时改变照片/录像的**全部**行为（而非只有菜单清单）。

### 6.3 函数指针表在 mask ROM

对 `FUN_405D30DC` / `FUN_405D458E` / `FUN_405D560C` / `FUN_405D5B22` /
`FUN_4103A3E4` / `FUN_4103A77D` 以及描述符族
`FUN_403E5529` / `FUN_403E7B1B` / `FUN_403E7C3F` / `FUN_403E7E94`：

- Ghidra **0 处直接调用**；
- 在块 0 内搜其 4 字节地址（±1）**全部 0 命中**（`tools/find_fn_ptr_refs.py`）。

⇒ **这些函数的指针表在机身 mask ROM 里**，
与「UI 框架在 mask ROM、实现在块 0」的分工一致。
⇒ **这也意味着**：哪个描述符被选中，**完全由块 0 写进 `+0x6B` 的那个字节决定**。
