## 2. 两个可直接复用的"新增滤镜"模板（已由伪代码证实）

### 模板 A —— 参数覆盖式（最低成本）

`FUN_4078849B` 与 `FUN_40788562` 中完全相同的这段：

```c
if (iRam605fcd3c == 0x32) {                 /* 当前是效果 50 */
    puVar2 = (undefined4 *)0x605fce7c;        /* 源：效果 50 参数模板 */
    puVar1 = (undefined4 *)0x605fcd44;        /* 目标：当前生效参数区 */
    iVar4 = -0x4e;                            /* 0x4E = 78 个 dword = 312 字节 */
    do {
        uVar3 = *puVar2; puVar2 = puVar2 + 1;
        *puVar1 = uVar3; puVar1 = puVar1 + 1;
        iVar4 = iVar4 + 1;
    } while (iVar4 != 0);
    FUN_407887e0(10);                        /* 切换到效果 10 的管线 */
    ...
}
```

⇒ **一个新滤镜 = 312 字节参数块 + 复用既有效果的 pass 管线。**
不需要写任何新的 DSP 代码。**这就是"新增创意滤镜"最现实的落地路径。**

### 模板 B —— 独立效果

新建效果 ID（下一个可用值 60）、独立参数块、独立 pass 函数，
并在 `FUN_407883DD` / `FUN_40788616` 的初始化序列里登记。

## 3. "解锁录像艺术滤镜"的具体落点

伪代码 `FUN_40788616`：

```c
uint FUN_40788616(uint param_1) {
  short sVar1;
  if ((param_1 & uRam602aeb94) != 0) {      /* ① 类型支持位掩码 */
      if (param_1 == 2) {
          sVar1 = FUN_407868fc(0x605fca00, 0x7e5c9809, 0);   /* ② 拍照参数源 */
      } else {
          uRam605fccc4 = 0x7e5c9b1c;
          sVar1 = FUN_407bc0be(0x605fccc4, 0x7e8973d0, 0);  /* ② 录像参数源 */
      }
      ...
  }
}
```

⇒ 录像滤镜的**参数本来就存在于机身 mask ROM**（`0x7E5C9B1C`），
固件只是搬运/使能。因此"解锁"只需改固件侧：

| 落点 | 地址/函数 | 改法 |
|---|---|---|
| **① 类型支持位掩码** | `0x602AEB94` | 置上录像类型对应的位 |
| **② 拍照/录像分支判定** | `FUN_40788616` 的 `param_1 == 2` | 让录像也走拍照那套完整实现 |
| **③ 效果级类型白名单** | 各效果的初始化函数（如 `FUN_4078846D` 调用 `FUN_4078866A(2)` + `FUN_4078866A(1)`） | 给缺失录像类型的效果补上 `FUN_4078866A(1)` |

> **注意**：`FUN_4078846D`（star_light）**同时**调用了 `FUN_4078866A(2)` 与 `FUN_4078866A(1)`
> ⇒ **有的效果拍照/录像都初始化，有的只初始化拍照 —— 这正是"电影艺术滤镜被锁"的形态。**
> 找出那些**只调用 type 2、不调用 type 1** 的效果初始化函数，就是逐个解锁的位置。

**调用关系（伪代码实证）**：

```
FUN_407883DD (总初始化)
   └─ if (效果ID == 0) { FUN_40788616(1); FUN_40788616(2); FUN_407887E0(10); }

FUN_4078846D (star_light)
   └─ if (ID == 50) FUN_40788562(0x46);
      else if (ID != 10) return;

      FUN_4078866A(1);   ← 录像
      FUN_407887E0(0);

   └─ if (t & 0x602AEB94) { t==2 ? 拍照路径 : 录像路径 }
```

**⇒ 关键判读**：`FUN_4078846D` **同时**调用 `t=2`（拍照）与 `t=1`（录像），
说明"**同时处理两种类型**"是正常形态。
若某个效果的初始化函数**只调用 t=2 而不调用 t=1**，它就是"该滤镜的录像形态被锁"的点。
**这是逐个滤镜解锁清单的判定标准。**

## 5. 重要边界：效果算法与参数在**机身 mask ROM** 里

从伪代码可直接读出参数区的**源头在 ROM**：

```c
/* 拍照路径 */
FUN_407868fc(0x605fca00, 0x7e5c9809, 0);   /* RAM 缓冲区 <- ROM 源 */
/* 录像路径 */
uRam605fccc4 = 0x7e5c9b1c;
FUN_407bc0be(0x605fccc4, 0x7e8973d0, 0);    /* RAM 缓冲区 <- ROM 源 */
```

| 结论 | 含义 |
|---|---|
| 滤镜的**像素算法 + 调校参数存在机身 mask ROM** | **固件补丁无法新增一种全新的滤镜算法** |
| 固件能改的是：**启用/禁用、类型白名单、参数区在 RAM 里的搬运与变体** | 「解锁」类目标**完全可行**；「全新算法」类目标**不可行** |

⇒ 因此"新增创意滤镜"应重新表述为两个可行目标：
- **A. 解锁 ROM 里已存在但被固件屏蔽的滤镜**（需要实机 ROM dump 才能确认 ROM 里还藏了什么；
  本项目已能枚举块 0 引用到的 ROM 地址，`0x7E5Cxxxx` 区间共 **120 个**不同地址被引用）
- **B. 给已有滤镜做参数变体**（`0x605FCD44` / `0x605FCE7C` 这类 312 字节 RAM 参数块
  在运行时可被固件改写 ⇒ 变体是可行的，但**变体的原始数据仍需来自 ROM**，
  除非变体本身由固件里的其它数据拼出）

> **诚实的边界**：要让"新增滤镜"完全成立，需要 **E-P5 实机的 mask ROM dump**
> （`0x7E000000–0x7FFFFFFF` 一带），或找到 ROM 里已备但未启用的效果。

## 6. 顺带确认的另一处镜头结构

`FUN_4048B6D2`（E-P5）反编译显示它是**镜头畸变校正**函数，
使用结构体 `+0x46C` 与 `+0x48C` 处的**每镜头标定表**，
并按 `*(byte *)(*obj + 8) * 0x10` 以 **16 字节步长**查表。
⇒ 机身确实存有**每镜头的标定数据**，与 cmdada `notes/autofocus.md`
所述"约 12 组每镜头 AF 参数块"相互印证。
