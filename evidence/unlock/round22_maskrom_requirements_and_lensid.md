## 1. 社区补丁第二处（镜头 ID 白名单）在 E-P5 的定位尝试 —— 穷尽性排查

### 1.1 参考实现（E-M1 III v1.2）

【观察】`FUN_40e773c9` @ 运行地址 `0x40E773C9`（块内文件偏移 `0x6773C9`）：

```
0x40e773cd  MOV 0x6079e3a9,A1      ; 白名单表（**mask ROM**，不在块 0 内）
0x40e773d3  MOV SP,A0
0x40e773d4  ADD 0x8,A0
0x40e773d6  MOV 0xd0,D1            ; -48 = 拷 48 字节 = 12 个 u32
0x40e773d8  SETLB
loop:  MOVBU (A1),D0 / INC A1 / MOVBU D0,(A0) / INC A0 / INC D1 / LNE
0x40e773e1  CALL 0x40e76c68        ; 镜头信息有效性判定
0x40e773e7  CMP 0x1,D0
0x40e773e9  BNE 0x40e77437         ; 无效 → 未识别
0x40e773ec  CALL 0x409f7005        ; 取镜头信息数组

0x40e7741d  MOV 0xff,D1            ; 0xFFFFFFFF 表尾哨兵

...
0x40e7742e  MOV (A1),D0

0x40e77432  MOV 0x1,D0
```

【观察】调用链：`FUN_40e773c9` ← `FUN_40e75b50`（薄封装） ← `FUN_40af6745` ← …

### 1.2 E-P5 v1.8：8 条路径全部落空

| # | 路径 | 工具 | E-P5 结果 |
|---|---|---|---|
| 1 | 16 字节上下文 `c8 0e a2 c8 0b db 50 91 71 a1 c8 04 a2 d9 71 a1` | `find_dispatch_by_fingerprint` | **0 命中** |
| 2 | 完整指令序列 `71 a1 c8/c9 XX 80 01 f8 92 04` | `find_whitelist_pattern` | **0 命中** |
| 3 | 松模式 `c8/c9 XX 80 01 f8 92 04` | 同上 | 42 命中，全是「置标志位=1」通用惯用法 |
| 4 | `71 a1 c8/c9 XX 80 01`（4 字节内） | 同上 | **0 命中** |
| 5 | `71 a1 c8/c9 XX`（10 字节内） | 同上 | 33 命中；抽检 0x404CDA99 = 事件链表函数、0x40D54D6F = `a<=b` 比较助手 |
| 6 | `MOV 0xff,D1` + `CMP D0,D1` + 紧邻分支 | Ghidra 全程序统计 | **0 命中** |
| 7 | 0x30 字节 ROM 拷贝循环 `85 XX db f0 41 45 f0 50 41 44 d9` | `find_rom_copy_loop` | E-P5 仅 2 处（`0x405DB2CF` src `0x7E562313`、`0x4107BF83` src `0x7EEF04E9`），**反编译核对后均非白名单表**（是配置表/字符串表类代码） |
| 8 | 24 位 ID 拼装序列 `f8 c2 08 f2 1e f8 c1 18 f2 16 f8 c0 10 f2 12` | 原块字节搜索 | **恰好 1 处** `0x403A62C9` —— **但它是另一套子系统**（§4），不是镜头白名单 |

**方法学自检**：同一套脚本在 E-M1 III 上跑，路径 7 精确命中 `0x40E773D6`（src `0x6079E3A9`），
路径 8 精确命中镜头 ID 拼装点 —— 证明工具本身有效，E-P5 确实**没有**这段结构。

### 1.3 结论

【观察】E-M1 III 的白名单表在 **mask ROM `0x6079E3A9`**（不在任何 `.BIN` 块内，
E-M1 III 块 0 只覆盖 `0x40800000–0x42200000`）。

【推断】**E-P5 v1.8 没有「镜头 ID 白名单」这道校验**（或它采用了完全不同的实现）。
⇒ **社区补丁的「改动 2（解除镜头 ID 白名单）」在 E-P5 上没有对应物**，
也就意味着 **E-P5 不会出现「换了副厂镜头就不认」的故障**。
⇒ 对目标②（解锁被锁住的功能）而言，这是**好消息**：E-P5 需要的只有改动 1（AF 步数上限）。

【未知】E-P5 是否以别的方式（例如按镜头型号字符串、按 serial）限制镜头，无法从 `.BIN` 判定。

## 2. 一条通用发现：24 位 ID 拼装是**共用助手**

【观察】下面这 14 字节在 E-M1 III（镜头 ID）与 E-P5（另一套参数表）里**完全相同**：

```
f8 c2 08 f2 1e   ASL 0x8,D2   / OR D3,D2
f8 c1 18 f2 16   ASL 0x18,D1  / OR D1,D2
f8 c0 10 f2 12   ASL 0x10,D0  / OR D0,D2
```

它把 4 个字节 `[b0,b1,b2,b3]` 拼成 32 位 `b1<<24 | b0<<16 | b2<<8 | b3`。
⇒ **跨机型、跨子系统的「ID 拼装」惯用法**，
⇒ 以后找某个 ID 的来源时，应优先搜这 14 字节，而不是搜具体的结构偏移。

### 3.1 附带：20 槽表 `0x40A56338` 在**块 0** 里（本轮复核，字节完全一致）

| 槽 | 指向 | | 槽 | 指向 |
|---|---|---|---|---|
| 0 | `0x7E5C9171` | | 10 | `0x7E5C9194`（默认） |
| 1 | 默认 | | 11 | `0x7E5C9142` |
| 2 | `0x7E5C913E` | | 12 | `0x7E5C9185` |
| 3 | `0x7E5C918F` | | 13 | 默认 |

【观察】槽 0–9 = 照片侧、槽 10–19 = 录像侧（第十二轮结论）。

## 4. 第二套「块 0 侧 ID + mask ROM 侧参数」架构（本轮新发现）

### 4.1 E-P5 v1.8 的 6 项参数表

【观察】`FUN_403A62B1` @ `0x403A62B1`（块内文件偏移 `0xE62B1`）：

```c
uint FUN_403A62B1(void) {
    uint *p = (uint *)0x7E429774;              // mask ROM 表
    for (i = 0; i < 6; i++, p += 2) {
        if (ID == *p) break;                    // ID 由 RAM 4 字节拼成
    }
    if (i < 6) {                                // 命中
        u32 src = p[1];                         // 该项的参数数组指针（ROM）
        for (j = 0; j < bRam60526982; j++)      // 长度来自 RAM
            *(u16 *)(0x60528912 + 2*j) = *(u16 *)(src + 2*j);
        FUN_403A51a0(1);                        // 置标志 0x605289E5 = 1
    }
    return 0;
}
```

| 角色 | 地址 |
|---|---|
| 32 位 ID（4 字节，RAM） | `0x6052695C` |
| 参数个数（u8，RAM） | `0x60526982`（上限 0x20） |
| 参数落地缓冲（u16 数组，RAM） | `0x60528912` |
| 命中标志（u8） | `0x605289E5` |
| **ROM 表（6 × 8 B）** | **`0x7E429774`** |

【观察】调用者 1 个：`FUN_403A052B`（`0x403A052B`），在循环里调用。
【观察】`FUN_403A51A0(x)` 只做 `uRam605289E5 = x`。
【观察】同一子系统还维护 `0x605289A2` 起的 32 项 u16 数组（`FUN_403A631D`）。

### 4.2 跨机型普查

【观察】同一段查表循环（`fc dc <imm32> 70 a2 c8 .. 44 20 08 a5 06 c4`）在：

| 机型 | ROM 表地址 |
|---|---|
| E-P5 v1.8 | `0x7E429774` |
| E-M5 v2.2 | `0x7E86FEE4` |
| E-M5 v2.3 | `0x7E8701A4` |
| E-M10 v2.3 | `0x7E8701A4` |
| E-PM2 v1.5 | `0x7E73B1E0` |
| E-PM2 v1.6 | `0x7E73B48C` |

⇒ **这是跨代、跨机型通用的架构**，不是 E-P5 独有。
⇒ 同时再次印证：**参数在 mask ROM，ID/长度/落点在块 0 的 RAM**。

### 4.3 意义

【推断】这条架构与艺术滤镜的「20 槽表在块 0、参数块在 ROM」**是同一种设计思路**：
奥记把「可变部分」（ID、槽位、落点）留在固件，把「参数内容」放进机身 ROM。
⇒ **任何「换一组参数做变体」的想法，最终都要面对 mask ROM。**
⇒ 反过来，**这给 mask ROM dump 提供了明确的验收清单**（§3 的 12 组）。

【未知】这套子系统具体是什么功能（色彩？白平衡？画质预设？曝光？）——
块 0 内该区域（`0x403A4xxx–0x403A64xx`）**没有任何可读字符串**，
`FUN_403889C1` / `FUN_403889D9` 解析的描述符来源也未追到。**待查。**

## 5. AF 步数上限效果的**可复现**计算表

【观察】第二十一轮的配方只抬 `cap`（`0x6CC` / `0x1C20` → `0xFFFF`），
但 `FUN_4058A207` 里真正生效的是 `min(cap, 量程上限)`，
量程上限 = `(0x800000 − thr) / (cnt + base)`。

【推断】各分支的**实际**上限（`tools/af_cap_effect.py`，可直接复跑）：

| mode | step | flag | thr | cnt | 量程上限 | 原 cap | **原生效** | 抬 cap 后 | 增益 |
|---|---|---|---|---|---|---|---|---|---|
| 3 | 6 | =1 | 0x340 | 0x1313 | 1595 | 0x6CC | 1595 | 1595 | — |
| 3 | 6 | ≠1 | 0x340 | 0x1037 | 1853 | 0x6CC | 1740 | 1853 | +6% |
| 3 | 3 | =1 | 0x340 | 0x0C66 | 2363 | 0x6CC | 1740 | 2363 | **+36%** |
| 3 | 3 | ≠1 | 0x340 | 0x098A | 2977 | 0x6CC | 1740 | 2977 | **+71%** |
| 3 | 4 | — | 0xA40 | 0x03D1 | 6202 | 0x1C20 | 6202 | 6202 | — |
| 2 | 5 | =1 | 0x190 | 0x16E4 | 1420 | 0x6CC | 1420 | 1420 | — |
| 2 | 5 | ≠1 | 0x190 | 0x1267 | 1762 | 0x6CC | 1740 | 1762 | +1% |
| 2 | 3 | =1 | 0x190 | 0x1267 | 1762 | 0x6CC | 1740 | 1762 | +1% |
| 2 | 3 | ≠1 | 0x190 | 0x0FCD | 2049 | 0x6CC | 1740 | 2049 | +18% |

【推断】**抬高 `cap` 只对 `step == 3` 的分支有实际增益**（最多 +71%）；
其余分支被量程公式卡住。
要复刻社区补丁「彻底无上限」的效果，还需抬高 `0x800000`
（`0x4058A256` / `0x4058A28C`，块内文件偏移 `0x2CA256` / `0x2CA28C`，字节 `fc cc 00 00 08 00`）。

【观察】溢出参考：输出按 `steps × 0x1E` 存 u32 ⇒ `steps ≤ 143 165 576`；
返回值 `steps × 600`（int）⇒ `steps ≤ 3 579 139`。
【未知】`0x800000` 这个量程常量的**出厂含义**未知（不是 u32 溢出边界），
因此抬高它的安全区间**必须实机验证**。
