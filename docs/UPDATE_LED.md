# E-P5：SD 更新时，为什么成功后还会闪灯

针对 E-P5 官方 1.8 MAIN 的 SD 更新路径：**处理更新请求时灯常亮；成功返回后进入较慢的均匀闪烁，并等硬件输入。错误分支也会闪，但周期更短。** 旧说明中「快闪一定还在写，必须等到灯自然熄灭」没有这段程序的支持。黑屏和闪灯持续了多久，都不足以单独区分成功与错误。

| 阶段 | 原版 MAIN 的证据（CPU 地址） | 指示灯通道 0 |
|---|---|---|
| 找到文件，处理更新 | `0x7e2070cd` 传入 FAT 目录名 `DCOLYMP    `；`0x7e206f22` 引用找到二进制文件的日志；`0x7e206f86` 设置模式 1，然后提交请求并等待回复（`0x7e206fa2`、`0x7e206fc3`） | 参数 255 走特殊分支，占空字段为 100，常亮。这覆盖处理期间，不是精确的闪存写入起止标记。 |
| 成功 | 回复和回复内的结果都为零，继续查下一个条目；遍历结束且至少接受了一个文件后，`0x7e207011` 以 `(3,2)` 调用 `0x7e585b40`，该函数打印 `Seikou`（成功），并于 `0x7e585b7b` 设置模式 2 | 参数 250，周期字段 249900，占空字段 50。随后进入等待。 |
| 错误 | 等待回复失败，或回复内结果非零，`0x7e206fd1` / `0x7e206fe2` 以 `(3,3)` 调用 `0x7e585c99`；该函数打印 `Shippai`（失败），于 `0x7e585ccd` 设置模式 3。早期初始化错误也可进这个处理函数。 | 参数 100，周期字段 99960，占空字段 50，闪动比成功分支快。它使用不同的等待条件。 |

两种闪烁用同一通道和同一 PWM 设置路径。`0x7e585f31` 起的整数运算为 `(15686 // (1000 // 参数) // 4) * 255`。两种周期字段的比是 2.5:1；尚无这台机身的光学波形或定时器计数方式实测，不能把常量 250 或主观描述「快闪」直接换算为已证实的 Hz 阈值。

成功路径以 3 为参数调用等待函数 `0x7e585da2`。`0x7e585dc9` 在条件未满足时跳回 `0x7e585dc0`，反复调用 `0x7e586077`。条件来源是 `0x7e14aed8` 读取的 `0x98e00058` 第 31 位；值为 1 才放行。循环没有超时计数。放行后 `0x7e585e03` 才选模式 5 停止此通道，继而进入写硬件寄存器的终止例程。失败路径则将 4 传给等待函数，不能套用成功路径的位条件。没有 E-P5 的线路图或现场寄存器记录，不能单凭此处的地址给该引脚命名。

这证明 **SD 更新程序认为操作成功后确实会持续闪灯**。它不能证明某一次更新已经启动了新固件、照片设置已生效、任何黑屏都在走上述代码，或所有底层故障都能被它检出。不要将其他机型的闪灯次数或 USB 更新屏幕直接套用到这里。

## 离线复核

在仓库根目录运行（不连接相机，不写固件）：

```sh
python tools/inspect_update_led.py
python tools/inspect_update_led.py --rc2 build/ep5-flash-20261113/RC2/DCOLYMP/E1089999.BIN
python -m unittest discover -s tests -p test_update_led.py -v
```

第一条命令要求已有解包的原厂 MAIN（可用 `--stock-main` 指定路径）。脚本按 SHA-256 限定原版，检查 MN103 的相对调用目标、返回值比较、成功/失败字符串引用、PWM 参数和等待循环。地址按 MAIN 基址 `0x7e101020` 给出。

第二条从实际 **RC2 SD 文件** 重新解码、检查容器校验，再逐字节比较 SD 更新程序、两种终态处理与灯控、PWM 驱动、硬件输入及对应字符串五个连续区间。RC2 容器 SHA-256 为 `90a63cd0b191f0d0cfdf344b2129723af07f6969d1d6368b8e2216a2019c1229`；全 MAIN 有 48 个字节不同，五个受检区间无差异。脚本会列出区间和各自哈希。这只验证此文件，不能证明机身当时已经安装了哪个版本。
