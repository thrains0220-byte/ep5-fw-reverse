# E-P5 原厂装载、ART 分配与中性显影路线

此次继续检查 OM-C 程序包中 E-P5 1.8 候选空间背后的启动指令，并向前追踪本项目 JPEG 接入点的生产者。**没有生成可安装固件，没有执行真实 ISP 显影。** 输入主程序 SHA-256 固定为 `dfe255e4d5a43329712c1fdfd6861ee1f3ef54a268b6096628bf045d8cc590df`，复用固定版本 CPU 引擎，不复制 OM-C 功能 payload。

## 启动读请求覆盖模块候选

执行原厂 `0x7e1011b0` 至 flash reader `0x7e10187b` 入口，得到以下真实指令构造的参数：

| 参数 | 值 |
| --- | --- |
| a0，源地址 | `0x402cf000` |
| a1，目的地址 | `0xbe110000` |
| d1，字节数 | `0xb1800`，727,040 字节 |

目的 uncached 区间 `[0xbe110000,0xbe1c1800)` 的 cached 别名是 `[0x7e110000,0x7e1c1800)`，覆盖完整的 `[0x7e128010,0x7e130000)` 模块候选。源地址减主块地址 `0x402c0020`、目的别名减 CPU 基址 `0x7e101020`，两者偏移同为 `0xefe0`。

这为 OM-C 选择该位置补上原厂读取请求证据，也解释了它的 loader_patch 为什么可能不必改字节。**模型在 reader 入口停止**，没有执行 flash/ECC/DMA；没有证明实际装载成功、后续内核/任务不覆盖该区，或 ART/JPEG 其他区段的装载完成。

## 原厂生成尺寸并申请缓冲区

`art_com_pass_init 0x7e40a20b` 经包装记录 `+8` 取得 ART packet。测试使用真实全局位置 `0x605f4510`：

| packet 偏移 | 已执行的作用 |
| --- | --- |
| `+76`，即 `0x605f455c` | 图像地址；非零复用，为零进入申请分支 |
| `+80`，即 `0x605f4560` | 六个 u16 几何记录，由原厂函数生成 |
| `+2` | 影响尺寸模式与内存池；本组使用 3 |
| `+96` | 输出比例表行索引；本组使用 1 或 2 |

**没有预置宽高。** 原厂尺寸表 `0x7e559f68`、尺寸模式函数 `0x7e409e80`、输出尺寸函数 `0x7e409f16`、比例计算 `0x7e3b114c` 执行后产生：

| 案例 | 六个几何 u16 | 申请字节数 |
| --- | --- | --- |
| 完整 4:3，比例索引 1 | `4608,3456,4608,3456,0,0` | 31,850,496 |
| 3:2 裁切，比例索引 2 | `4608,3456,4608,3072,0,192` | 31,850,496 |
| 已有缓冲区 | 同 4:3，保留既有地址 | 不再申请 |
| 申请失败 | 同 4:3，图像地址零，原厂返回 1 | 进入原厂错误报告 |

上述分支支持“存储宽高、有效区域宽高、偏移”这一解释。申请分支将第一个宽高相乘后乘 2，经原厂 `art_buff_alloc 0x7e40a3fc` 到 `0x7e23e0a2`。**仅最后的内存池例程由模型返回合成地址或零，不创建像素。** 分配大小不能证明 YUYV 次序或 BT.601 全范围。

成功案例接着执行原厂 `rec_art_make_prim 0x7e3ed85c`，读取刚生成的全局，将同一地址与前四个几何 u16 送入 `0x7e3f4884` 的 40 字节 JPEG 请求。JPEG 本体是收集参数/返回 `0x1234` 的服务模型，没有创建 JPEG。

这明确了当前胶片适配器限制的意义：存储和有效尺寸不同就跳过。不能将这条 3:2 路线的容量误算成 `4608×3072×2`，忽略其 3456 行存储和 192 行偏移。

初始化后紧接 JPEG 是探针串接两个原始函数来检查全局传递，**真实固件在二者之间还需要 ISP 显影与完成通知**。失败案例不调用 JPEG 是探针策略，并非已证明原厂所有失败路径都会阻止编码。

## 中性列表保留转换，省去附加滤镜

执行原厂 `art_set_filter 0x7e40b368` 及其列表/效果选择函数，使用全新的合成任务记录：

| packet 内容 | 原厂 initializer | 原厂函数列表 |
| --- | --- | --- |
| `+6=0`，`+8..+16` 的附加效果为零 | `0x7e40a20b` | `0x7e40cbb1` |
| `+6=73`，同样关闭附加效果 | `0x7e40a20b` | `0x7e40cbb1`、`0x7e40115c` |

`0x7e40cbb1` 是原厂 `art_stl2ycc` 包装入口，`0x7e40115c` 对应针孔滤镜。原厂列表构造可以保留 RAW→YC，省去该附加滤镜。**这尚不证明中性 packet 在完整任务调度/ISP 中成功，也不证明输出符合标准色彩空间。** 没有验证复用旧任务记录的所有状态。

静态追踪还看到 `rec_art_exec 0x7e3ed7e6` 一带设置 packet、经 `0x7e3fca97` 投递，再由 `0x7e3f7fa7` 等待 12 字节回复。任务完成、错误、释放与后续 JPEG 的完整时序仍需串接验证。

## 接下来的固件集成

首版优先研究复用一个已有 ART 选项：在原厂设置 packet 参数之后，使本次艺术滤镜和附加效果中性化，保留 RAW 显影参数和完整 4:3 尺寸；显影完成后运行内置 LUT，再交原厂 JPEG。这是当前选定的集成候选，尚未安装第二个固件钩子或实现菜单选择。

仍需落实真实完成/释放、普通拍摄模式入口、像素/颜色契约、缓存与长耗时调度、运行期驻留、关闭/恢复、ORF 保留和实机成片。现有色彩模块继续默认关闭；本轮不以无效果升级包代替用户要的胶片模拟固件。

## 复现与验证边界

```bash
python3 tools/native_contracts.py data/ep5-decoded/00_0100_402c0020.decoded.bin \
  --out generated/native-contracts-check.json
python3 -m unittest discover -s tests -p test_native_contracts.py -v
```

报告路径必须尚不存在。[验证记录](native-contracts-verification.json)包括源码/CPU 引擎哈希和合成服务边界。日志/跟踪/错误报告只按原厂帧返回，分配器只返回地址，编码器只记录请求。写入仅允许映射栈、packet、一个任务记录及启动小段全局，其他写入立即终止。没有相机 I/O 或升级容器输出。

最终整套测试 48 项通过、无跳过。独立审查纠正了针孔滤镜的命名，补强裁切容量/错误返回断言；另修正五个相关 CPU 探针的主机指针运算，并通过破坏 codec 返回值的故障注入确认命令行不会误报成功。此前的验证 JSON 保留为对应提交时的历史快照，新报告记录当前探针源码哈希。
