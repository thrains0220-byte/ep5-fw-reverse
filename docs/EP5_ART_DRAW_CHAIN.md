# E-P5 ART/OSD 绘制链路

本记录覆盖 E-P5 1.8 解码 MAIN 的静态分析和离线 CPU 执行。
复现工具仅读取项目锁定的 MAIN。其 SHA-256 为
`dfe255e4d5a43329712c1fdfd6861ee1f3ef54a268b6096628bf045d8cc590df`。

## 可复现工具

```text
python tools/inspect_art_draw_chain.py --out build/art-draw-chain.json
```

工具以字符串指针引用作为反汇编导航锚点。每个地址是“包含该字符串
引用的指令地址”，不是已经证明的函数入口。输出明确标记
`camera_accessed=false` 和 `firmware_created=false`。

## 与已有 ART 状态机的关系

### 进入回调的新增证据

`tools/inspect_art_callbacks.py` 对官方 MAIN 的 MN103 反汇编做了哈希保护，
把两个进入回调的直接调用边和间接 vtable 调用单独列出。第 5 列入口为
`0x7eaf19b7`，第 6 列入口为 `0x7eaf1a46`；两者都读取对象全局
`0x602c0d1c`，随后通过对象 vtable 的槽 0 和槽 8 调用。两条路径的事件
常量分别为 `0x91` 和 `0x9d`，并共享资源/状态服务调用。

这使“ART 进入回调 → 对象方法分派”的关系可复现，但仍不能把 vtable 槽
当作已知绘制函数。对象类型、槽位签名、绘制成员和 Display API 参数仍需
进一步恢复。工具输出明确保持 `camera_accessed=false`、
`firmware_created=false`。

校正：第 6 列 `0x7eaf1a73` 是间接 `calls (a1)`，不是直接调用
`0x7eb1e5b5`；两个间接调用的 site 应记在 `calls` 指令而不是此前的指针装载指令。
工具现逐条核对原始指令和 PC 相对目标，不再仅凭整包哈希检查手工清单。

进一步从正确偏移读原始表：两个进入回调先分配 4 字节临时对象并将其首字设为
`0x7edbfa8c`；该表首个指针为 `0x7eb1e11d`，所以临时对象槽 0 的间接调用可连接
到此分派器，并分别传入 `0x91/0x9d`。分派器随后创建或选择对象并写入
`0x602c0d1c`。这只建立了进入链中的一条静态边；尚未证明生成对象的类型、绘制
函数、线程上下文及真实 UI 行为，不能直接把它用作修改固件的入口。

进一步对 `0x91` 按三个原厂分派表逐级解表，实际落在 `0x7eb1e329`，调用
`0x7eb28b4b`：分配 432 字节对象，构造器 `0x7eb28b7a` 设置虚表
`0x7edf7c88`。虚表偏移 `+12` 指向事件方法 `0x7eb29265`，其事件 0/1 分别调用
`0x7eb292db/0x7eb29305` 改对象 `+416` 的选中下标并调用 `0x7eb28d11` 重绘。
`+412` 指向描述符 `0x7edf7bdc`（列表 `0x7edf7908`、设置 ID `0x119`、13 项，
每项 44 字节）；`+420` 指向可用性数组。13 是原厂 ART 菜单条目数，针孔 I/II/III
是一个条目的变体，不能把此前 14 个载体槽误认为屏幕上有 14 个一级菜单项。

### 原厂事件的离线执行验证

`python3 tools/validate_art_object_probe.py` 在固定版本 MN103 CPU 模型上执行原厂
`0x7eb29265` 的事件 0/1：14 个合成状态覆盖普通移动、首尾回绕、跳过不可用项、
以及对象 `+429` 非零时不移动。检查选择字段、对象其他字段不被写入、返回栈指针和
被调用方保存寄存器。绘图入口 `0x7eb28d11` 及日志入口 `0x7eb1a475` 被替换为
按各自调用帧返回的模拟桩，**并未执行实际绘图、日志或相机任务调度**。事件编号到
物理按键的映射、无效指针或列表长度仍未确认。这一结果不是可刷写许可。

还观察到一项约束：选择查找把任何非零可用性值视为可选（模拟中值 2 被选中），但
`0x7eb28d11` 的页面组装循环在 `0x7eb28d73` 明确比较值是否等于 1。未来写入该
数组的集成代码必须维持 0/1，不能仅假设任意非零值都会被绘图路径接受；实际绘图
结果尚未运行验证。

13 项全部不可用时，模拟事件 1 从第 4 项得到索引 13（越过 0–12 的有效范围），
事件 0 得到 0；绘图被替换，不能推断后续后果。集成必须避免将全不可用列表交给原厂
导航，且应在使用索引前做边界检查，不能把原厂逻辑当作输入校验。
上述表、关键指令和输入哈希由 `tools/inspect_art_object.py` 检查；文字资源、
列表替换时的对象生命周期及真实显示仍未完成验证。

### 原厂页面组装的离线执行验证

`python3 tools/validate_art_render_probe.py` 在同一 CPU 模型中执行完整的
`0x7eb28d11`，对 13 个原厂条目和 6 个稀疏可用项共 19 个状态检查分页、选中项、
页面中每行的资源 ID，以及返回时的栈和保存寄存器。模拟中每页最多 4 个可用条目；
条目的普通与选中资源 ID 分别来自 44 字节记录的 `+6/+8`，页索引按可用项序号计算。
每次组装调用三次 `0x7ea13b5f`，参数分别是 `(58,188,obj+200,1)`、
`(0,12,obj+388,1)`、`(15,12,obj+400,1)`，以上参数顺序为 D0、D1、A0、A1。

截至 11 月 15 日，探针将初始化、更新、设置读取和服务方法替换为明确的模拟桩；它证明的是在这些
合成返回值下原厂代码构建了预期的数据，**不证明实际服务会显示文本、同步复制数据、
支持自定义资源或可从其他任务调用**。静态反汇编显示 `0x7ea13b5f` 转入
`0x7ea13cd1`：后者经表项的更新回调或内存复制路径处理，再进行后续通知；表项指针、
锁、回调及资源生命周期仍须单独恢复，不能据此直接修改显示服务。

### 2026-11-16：执行原厂 GUI 数据交接

现有页面探针已进一步执行原厂 `0x7ea13b47/0x7ea13c58` 读取、
`0x7ea13b5f/0x7ea13cd1` 更新、`0x7e10646f` 复制、观察者列表遍历和
`0x7ea142e7` 脏位标记。设置读取、辅助服务、同步回调和最终通知仍用模拟桩。
[本轮可复现报告](ep5-art-gui-transfer-verification.json)记录具体范围与源码哈希。

**更新表的来源：** 原厂启动代码 `0x7e101198` 保存初始化数据末端
`0x7e5ab3e4`；`0x7e1011ea..0x7e1011fc` 请求从 flash `0x4074e000`
装载 `0x1c3e4` 字节到 uncached `0xa02a9b40`，对应 cached `0x602a9b40`。
按 MAIN 的 flash/CPU 映射，源数据在 `0x7e58f000`。GUI 启动代码
`0x7eab79d7..0x7eab79e0` 用 `0x602be350`、数量 168 调用注册服务
`0x7ea13b00`。因此该表的初始字节位于 MAIN `0x7e5a3810`，每项 16 字节。
`inspect_art_object.py` 校验这些原始指令、表范围和三项内容；没有执行整机装载。

| 更新编号 | 读取回调 | 更新回调 | 数据缓冲 | 字节数 | ART 对象内来源 |
|---:|---:|---:|---:|---:|---|
| 0 | 0 | 0 | `0x606eb274` | 12 | `obj+388` |
| 15 | 0 | 0 | `0x606eb452` | 12 | `obj+400` |
| 58 | 0 | 0 | `0x606f1670` | 188 | `obj+200` |

这三个**初始表项**的回调为空，读取/更新走直接复制分支。表在真实运行时是否被改写
尚未验证。探针映射原始表字节，只给这三个目标缓冲分配带保护区的合成内存；管理器
和一个观察者为合成夹具，不代表真实对象已成功初始化。

在该夹具下，原厂页面读回旧数据后组装新数据，三次更新均：调用前置同步回调、
复制 `min(请求长度, 表项容量)` 字节、设置观察者对应编号的脏位、调用后置同步
回调，最后按通知参数调用通知入口。探针将两个同步回调建模为锁获取/释放，核对
调用顺序、持锁状态、复制完成后才通知、返回帧与保存寄存器。

本轮执行共 36 个场景：原有 19 个页面场景、9 个更新边界、8 个读取边界。

- 精确长度完整复制；超长请求被截到表项容量，并返回 1。
- 7 字节请求仅复制 7 字节，目标尾部保持原值；读取也遵循同一上限。
- 零长度但非空指针返回 1；更新仍标脏，通知开启时仍调用通知入口。
- 空指针、编号 168（首个越界编号）、空管理器返回 0，不改目标或标脏。
- 模拟锁获取失败返回 0，不复制、不释放未获取的锁、不标脏或通知。
- 关闭通知仍复制并标脏，但不调用通知入口。

所以未来适配层必须校验**精确长度、有效编号、指针和数据所有权**；返回 1 并不
保证整条消息已交付。这里复制的是数值/资源 ID 组成的页面数据，不能据此把 UTF-16
文本指针放进资源 ID 字段。动态名称的文本资源契约仍需独立恢复。

原厂通知入口 `0x7ea1431c` 将 `0x1900` 和目标对象写入消息，由
`0x7ea0b817` 入队。同一页面连续三次通知合并为一次唤醒；探针通过
`0x7ea0b96a` 取出该消息并确认槽位清空，再把出队字节交给
`0x7ea15c5f`。探针使用原厂基础虚表 `0x7ec6e538`。原厂
`0x7ea14578` 通过目标对象调用基础刷新方法
`0x7ea16b2a`。此方法从对象 `+2008` 取观察者，通过 `0x7ea14214` 复制并清零
21 字节脏位，然后向根对象派发 `0x1902`。探针核对回调收到的观察者和已复制的
脏位快照，接着由原厂迭代器 `0x7ea17118/0x7ea17133` 遍历两个子对象，按顺序
向它们和附加视图分别派发 `0x1901`。空子对象列表路径派发 `0x1902` 后返回
`-1`，不会派发 `0x1901`。

观察者探针从空链表开始，执行 `0x7ea1413a` 注册、`0x7ea141d3` 绑定、
原厂更新和刷新，再执行 `0x7ea14163` 注销。核对两个位图缓冲初始清零，
注销时先摘除链表节点再释放分配，注销后再次更新不会通知旧对象。
原厂清理路径在 `0x7ea13196` 调用按目标清队列的 `0x7ea0bb28`。探针通过
原厂更新排入一次 `0x1900`，在其后放入同编号、不同目标的消息，再运行清理函数。
原厂代码移除旧对象的消息，将另一条完整移到队首，随后原厂出队函数照常取出它。
实际 ART 退出是否总经过这条入口、队列清理与对象销毁的跨任务顺序仍需核对。
对象集合、视图事件处理、内存分配、锁和信号由夹具提供。
复跑 `python3 -m unittest discover -s tests -p test_art_render_probe.py -v`。

`tools/inspect_art_state_machine.py` 读取以下静态结构：

- descriptor：`0x7edc0284`，11 个状态列、64 个事件行、183 个回调、64 个事件。
- 事件矩阵：`0x7edbff6c`；回调指针表：`0x7edbfc90`；事件表：`0x7edbfa90`。
- 进入回调表：`0x7edc022c`；退出回调表：`0x7edc0258`。
- `0x9031` 和 `0x9032` 的矩阵项分别能选到 `0x7eaf1fa3` 和 `0x7eaf2fb3`，但探针停在回调入口，不执行回调主体。

因此目前可以建立“事件矩阵 → ART 回调日志锚点 → Display API 资源锚点”
的静态研究路线，尚不能建立真实设备上“按键 → 状态对象 → 绘制 → 文本出现”
的完整执行证据。

## 不能从这些地址推出的结论

这些字符串引用不能证明：

1. 候选地址就是可直接调用的函数入口；
2. 某个 OSD API 的参数布局已经恢复；
3. ART 进入、绘制和退出回调一定经过上述每个 API；
4. 自定义字符串可以安全挂接到原厂字体/OSD 缓冲；
5. 在 ART UI 中加入动态 LUT 列表或强度控件不会破坏原厂状态机。
