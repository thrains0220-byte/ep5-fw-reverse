# E-P5 1.8 原厂文件服务映射（只读逆向）

2026-11-14。输入 MAIN SHA-256 `dfe255e4d5a43329712c1fdfd6861ee1f3ef54a268b6096628bf045d8cc590df`。
本页只记录反汇编证据，不生成固件、不访问相机。用于 D 诊断分支复用原厂写服务把观测落卡。

## 服务封装结构

每个文件操作是一个 veneer：先调 `0x7e2914f1`（后端选择，返回 0=消息式 / 非 0=直接），
再走两条后端之一：
- **直接后端**：`0x7e296xxx` 系列函数。
- **消息后端**：`0x7e13452b`，D1=消息号（0x10000+子号），A0=栈上参数块，
  参数块首字来自全局 `0x7e11f938`（服务通道句柄）。

## 已确认入口（CPU 地址 / 消息号 / 返回帧 / 参数）

| 操作 | veneer 入口 | 消息号 | ret 帧 | 参数（GCC 视角） | 直接后端 |
|---|---|---|---|---|---|
| open | `0x7e291515` | 0x10001 | [a2,a3],28 | path=A0, mode=A1 | 0x7e2960db |
| close | `0x7e291557` | 0x10002 | [a2],16 | file=A0 | 0x7e29640e |
| **write** | `0x7e29159b` | 0x10003 | [d2,d3,a2,a3],40 | buf=A0,size=D0,count=D1,file=A1 | 0x7e296798 |
| read | `0x7e2915ea` | 0x10005 | [d2,d3,a2,a3],40 | dst=A0,size=D0,count=D1,file=A1 | 0x7e296da5 |
| (单参) | `0x7e291639` | 0x10007 | [a2],16 | file=A0 | 0x7e297053 |
| (双参) | `0x7e29167b` | 0x10008 | [d2,d3,a2],32 | D0,D1,A0 | 0x7e297076 |
| (单参) | `0x7e2916c5` | 0x1000a | [a2],16 | file=A0 | 0x7e297281 |
| (双参) | `0x7e291707` | 0x1000c | [d2,a2],24 | D0,A0 | 0x7e29728e |

注：现有运行时 veneer 把 read 入口标为 `0x7e2915ea`（消息号 0x10005），与本文一致。
write 入口 `0x7e29159b`（消息号 0x10003）与 read 参数结构完全镜像（4 参 ret40），
其直接后端 `0x7e296798` 检查文件结构 +312 的写标志位（`btst 16`）后进入写分支
`0x7e2967e0`；read 后端 `0x7e296da5` 走读分支。两者都经 `0x7e295898` 做句柄校验/锁
（`btst 1/2` 为读/写锁标志），故 `mov 1,d0` 不是方向标志，方向由各自后端分支决定。

## write 语义证据

`0x7e296798`：
```
mov a0,a3 ; mov d1,d3 ; mov d0,d2 ; mov a1,a2 ; mov a2,a0
mov 1,d0
call 0x7e295898,[a2,a3],12      ; 句柄校验/取锁
...
mov (312,a2),d1 ; btst 16,d1    ; 检查写允许标志
beq ...                          ; 不允许则跳过
call 0x7e296a1f / 0x7e2967e0    ; 写数据分支
```

## 复用方式（D 诊断分支）

write veneer 与现有 `_ep5_file_read` 同构（4 参、ret40、callee-saved d2/d3/a2/a3）。
诊断模块新增 `_ep5_file_write`：GCC 参数 D0=buf,D1=size，栈参 SP+12=count,SP+16=file，
映射到原厂 A0=buf,D0=size,D1=count,A1=file，`call _ep5_native_file_write,[d2,d3,a2,a3],40`。
链接脚本新增 `_ep5_native_file_write = 0x7e29159b;`。

## 边界

- 未验证真机 SD 挂载/根路径/写权限；诊断分支首次上机须先验证 open("wb") 成功。
- 消息后端通道句柄 `0x7e11f938` 在 ART 任务上下文是否有效，需真机确认。
- 写服务可能阻塞/耗时；释放钩子是否允许写文件、是否属于安全任务上下文尚未证实。最新实现一次可能重写最多 1024 字节；不能以旧模型中单条 128 字节来推断实际耗时。

## 2026-11-14：FILEFGND 投递、等待与 UI 读卡线索（静态证据）

以下地址均针对本页开头固定哈希的 E-P5 1.8 MAIN；未执行真机或完整任务模拟。可用 `toolchains/mn103/bin/mn10300-elf-objdump -b binary -m mn10300 -D -z --adjust-vma=0x7e101020 --start-address=起点 --stop-address=终点 data/ep5-decoded/00_0100_402c0020.decoded.bin` 在 WSL 复现。反汇编起点需选已知指令边界。

### 任务与分派

- 名称表中 `0x7e160762` 是半字 `0x12`，紧随其后的 `0x7e160764` 是 `FILEFGND`；任务描述符中对应编号 `0x12` 的条目入口指针位于 `0x7e119828`，值为 `0x7e28dd2f`，后续字段有 `0x0b`、`0x1000`。这些关联支持 FILEFGND 主循环身份；尚未单独执行启动任务注册或解析所有字段。
- `0x7e28dd2f` 的循环在 `0x7e28dd36` 调 `0x7e28de40`，后者从半字通道 ID `0x7e11f938` 通过 `0x7e295329 → 0x7e131208` 接收 16 字节消息，参数为 `-1`。循环按消息 `+8` 的高 16 位选择分派器，`0x10000` 类由 `0x7e2912f3` 处理，完成后经 `0x7e28de65 → 0x7e2952ef` 回复，再回到循环。`0x7e28dcba` 用同一通道 ID、名称 `FILECLBK_UEXEC` 调初始化包装 `0x7e1311d8`；该包装本身立即返回，不能据此宣称完成真实的队列创建。
- `0x7e2912f3` 查 `0x7e485a54` 跳转表：`0x10001 → 0x7e29131c → 0x7e2910d1 → 0x7e2960db`（open）；`0x10003 → 0x7e291332 → 0x7e2910f2 → 0x7e296798`（write）；`0x10005 → 0x7e291346 → 0x7e291115 → 0x7e296da5`（read）。参数由消息 `+12` 指向的结构取得，结果写回结构首字。

### 直接执行与同步消息

- `0x7e2914f1` 只有当 `*(0x8050)==0` 且 `0x7e111b3e` 在栈上返回的半字与 `*(u16*)0x7e11f59a` 相同，才返回 1，令文件 veneer 直接调用实际后端；否则返回 0 走消息路径。E-M10 上游 `notes/system.md` 和 `openkernel/port/portmacro.h` 将 `0x8050` 定义为当前 CPU 核心号，本机 E-P5 代码用法与此一致，仍属于跨型号佐证而非本机硬件测量，不应称为启动或中断标志。
- `0x7e111b3e` 根据 `*(0x8050)` 索引 `0x8ff00004` 所指结构，检查每核状态，再从结构 `+96` 指针所指对象的 `+16` 读取半字并写入调用者提供的地址；异常状态返回错误。它与文件任务 ID 比较，强烈表明该半字是当前任务标识；结构的完整语义和错误路径在 E-P5 尚未动态证明。`0x7e2914f1` 未检查 helper 返回码，不应把异常上下文当成已安全覆盖。
- 非直接的 open/read/write 将参数结构和消息号交给 `0x7e13452b`。该入口按通道 ID 的 `0x8000` 位选择 `0x7e134547` 或 `0x7e13460b`；对前者，`0x7e1345c6` 调 `0x7e1312a1` 投递，`0x7e1345df` 调 `0x7e131208` 等待响应，传入 `-1`。`0x7e131208` 底层分支的诊断字符串分别为 `OlyQeRdCpu` 和 `OlyQeRd`，表明队列读取路径；`0x7e1312a1` 的对应字符串是 `OlyQeWrCpu` / `OlyQeWr`。`-1` 是调用传入值，其精确内核超时语义尚未以 E-P5 内核执行验证；结合这一等待与响应结构，可以判断该 veneer 是同步调用，不能当作 UI 的异步文件接口。另一分支 `0x7e13460b` 的完整跨核等待路径仍待独立分析。
- GUI 任务若走该同步分支，调用期间 UI 任务会等待文件服务完成/失败；即便 30 KiB 顺序读取在理想卡上很快，挂载、卡故障、锁、目录扫描、跨任务依赖与看门狗可能远比数据传输耗时更重要。没有实机时延分布、GUI 锁持有情况和取消证据，不能宣称在 ART 绘制或按键回调同步读 LUT 安全。

### 可借鉴的异步组织与边界

E-P5 原厂 `0x7e27c3fd` 构建 `PARAMDT` / `CP??????CSV` 相关请求，随后经 `0x7e141955 → 0x7e13fe11` 建立带回调地址 `0x7e13fe9a` 的描述符，并调用 `0x7e28698f`；这是可研究的原厂描述符／回调机制线索，不足以证明其为可供 GUI 直接使用的通用后台预读 API，也未证明该路径不会等待。尚未找到经过验证的现成异步 LUT 读接口或缩略图预取契约。

上游 E-M10 的 `external/em10-fw/notes/plugins.md` 和 `plugins/loader/loader.c:file_idle` 记录了更直接的模式：GUI 只设请求标志，FILEFGND 循环处理读写并发布结果；该项目也报告过 GUI 回调读卡导致真机冻结，模拟器未重现。**这是架构参考，不证明 E-P5 同样的 hook 已安全。** 推荐在 E-P5 上继续验证文件任务调度点、任务退出/重入、所有权、唤醒、缓存一致性和超时；UI 只消费有界的已发布快照并显示加载/失败状态。后台 worker 必须有经过证明的上下文；不得在 FILEFGND 中同步等待自己的请求，也不得将未审计地址当成异步接口。是否必须在 FILEFGND 本身读卡，目前不能由静态证据断言。
