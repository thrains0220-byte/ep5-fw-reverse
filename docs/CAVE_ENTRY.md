# E-P5 胶片模块：完成资格、参数探针和颜色处理

当前源码把四个原厂调用点接入同一个模块：ART 参数发送前的单字段探针、接收 ART 回复、JPEG 编码前的 LUT、图像释放前的清理。**这是默认关闭的机身移植候选，不是可刷升级包。** 控制记录中 `enabled=0` 保留原厂，`enabled=1` 是原有 LUT 实验，`enabled=2` 才运行本次参数探针；两条实验路线不会同时启用。

## 布局和原厂调用点

继续使用 [OM-C 案例中独立复核的 E-P5 空间](OM_C_DBV040_REVIEW.md)，没有复制其光圈环 payload。官方 1.8 主程序必须匹配精确 SHA；四个旧指令都须逐字节一致。替换只应用于受限模型的内存映像。

| 调用点 | 原厂作用 | 模块行为 |
| --- | --- | --- |
| `0x7e3ed835`，原7字节 | 调用 ART packet 发送包装器 `0x7e3fca97`，帧 `[d2,a2],20` | 仅实验模式2且模式/变体/几何/原值全部匹配时，将本次 packet `+157` 从0设为1，再按原帧发送并恢复原调用点 MDR |
| `0x7e3ed850`，原7字节 | 调用接收包装器 `0x7e3f7fa7`，帧 `[],20` | 先使回复字段无效，执行原接收函数，检查结果与回复内容，再记录上下文/图像地址 |
| `0x7e3ed8d1`，原5字节 | 调用 JPEG `0x7e3f4884`，帧 `[d2,d3,a2,a3],16` | 检查并消耗匹配资格，运行颜色核心，再按原帧调用 JPEG |
| `0x7e3f2476`，原5字节 | 调用释放辅助 `0x7e3edac1`，帧 `[],4` | 清除未消费的资格，再执行原厂释放辅助 |

完整模块 **31,838 字节**，剩余 **914 字节**，结束 `0x7e12fc6e`；SHA-256 `a862479741b1d4ac7548bed5696ab277b1bf789cc976fdd90ad911e110c7a531`。

| 数据 | 当前地址 / 大小 |
| --- | --- |
| 六字只读控制记录 | `0x7e128920` / 24字节 |
| 资格状态的存储位置 | `0x7e128938` / 8字节，镜像初值全零 |
| 资格状态的访问地址 | `0xbe128938` / 同一物理存储的 uncached 视图 |
| 原创 Warm Negative RGB16 LUT | `0x7e128940` / 29,478字节 |

链接器只接受一个 LUT、24字节控制及8字节显式状态，拒绝越界和其他 data/BSS。普通 MN103 与 AM33 解码须一致。此前31,126字节布局和15案例验证保留在旧提交/历史证据中，不代表当前模块。

## 路线 A 的单字段实验

原厂 `rec_art_exec` 在参数构造后、发送前的 `0x7e3ed835` 仍保有 `a2=0x605f4510` packet 与 `a3` 拍摄上下文。本次跳板保留所有通用寄存器、栈和原厂返回值，调用原发送包装器后把 MDR 恢复为原调用点后继 `0x7e3ed83c`。只在控制值2、原始模式值105/变体1、packet滤镜码73、4:3以及四个几何半字均为4608/3456、上下文与packet原对比度为0时，改 packet `+157` 一个字节为1。控制值0/1、错误标签、其他模式/变体/比例/几何/原值都原样发送。

这只是观察颜色方向的**默认关闭实验**：固定 packet 的任务串行所有权、`+157` 的真实像素消费者、模式在机身菜单的显示名、RAW+JPEG/单拍设置及改动后的成片均未验证。`control[1]=2` 只在 CPU 模型中设置，没有安装或启用步骤。不能把它当作已完成的一款风格。

## 为什么必须继续执行原厂接收包装器

原厂 `rec_art_exec` 等待后仍返回保存的发送状态，没有在所追踪的尾部检查回复错误码。向下执行 `0x7e3f7fa7 → 0x7e131208` 后又发现：后者将底层非负接收长度转为成功 **0**，并不返回12。底层 `-50` 在这条等待路径被转换为 `-2`，其他测试负值被转换为 `-1`。

因此完成条件不是“返回12”或“走到了JPEG”。当前候选要求包装器返回0、回复u16状态0、回复word1为1、回复word2为原厂 packet 地址 `0x605f4510`，并关联当时的非零图像地址和 a3 上下文。接收前填入无效状态/token及零packet；即使原栈有一份旧的合法回复，短回复也不能继承旧字段而通过。

接收桥在原接收函数返回后保存实际寄存器/MDR，再调用 GCC；第三个 GCC 参数放在栈+12，保存区从+16开始。验证比较的是原厂包装器返回后的状态，而非错误要求它不改变调用前的易失寄存器。

## 资格只用于第一次匹配的 JPEG

资格由两个u32组成：上下文和图像地址。JPEG入口必须同时匹配，且在任何像素写入之前清零资格。第二次JPEG请求不会重复套用 LUT。原厂释放调用点也清除尚未使用的资格，覆盖先释放、再复用同一地址但没有新完成通知的情况。

这些是**单次已观察回复之后的局部约束**。回复中的token固定为1，packet也是固定地址，没有逐次拍摄的nonce；上下文/图像地址从当前调用者和全局采样，不是回复回显。跨拍摄延迟到达的完整旧回复、任务并发和缓存所有权仍未解决，不能据此声称完整防重放或真实显影完成时序已验证。

## 图像和默认关闭

控制记录仍只生成 `tag=0x43355045`、其他字段零，没有实机启用选项；关闭情况下不修改像素、资格状态或 ART packet。模型中的启用记录是合成测试输入。

既有范围/容量/几何/编码/强度检查继续执行，额外保护模块的 cached/uncached 两个视图，以及 JPEG 请求在DRAM的另一个视图。缓存视图 `0x60000000..0x7fffffff` 和非缓存视图 `0xa0000000..0xbfffffff` 只能在确认的窗口内换算。模型已重现缺少请求别名检查时的调用栈破坏，修正后拒绝该映射。

像素仍显式假设 Y0/Cb/Y1/Cr、BT.601全范围；存储/有效几何须相同。没有接入看门狗/协作调度，也没有给此同步入口提供取消回调。拒绝资格只跳过 LUT，仍保留原厂 JPEG 调用，不替代原厂错误处理或保存策略。

## 证据与复现

29个目标指令案例覆盖原有像素/范围检查，以及缺少完成、接收失败/超时、8或11字节短回复、错误状态/token/packet/context/buffer、重复JPEG、释放后地址复用、模块和请求的地址别名。有效像素处理用实际编译代码，与主机参考逐字节比较；集成像素夹具为80像素，不声称已在相机中处理完整照片。

原始接收尾部、接收包装器、JPEG请求构造及释放调用片段均执行原版指令；它们由探针分别驱动，并非完整任务调度。模型化边界为本地队列路由判断、底层队列收取、日志/错误输出、JPEG本体和最终内存池释放。原厂释放辅助确实清零全局图像地址。没有真正分配/显影/编码像素，也没有访问相机。

```bash
python3 tools/cave_entry.py data/ep5-decoded/00_0100_402c0020.decoded.bin \
  --out build/ep5-completion-module
python3 tools/cave_entry.py data/ep5-decoded/00_0100_402c0020.decoded.bin \
  --check --out generated/completion-gate-check.json
python3 -m unittest discover -s tests -v
```

输出路径须尚不存在。模块生成 `film.elf`、`film.bin`、反汇编及包含四处字节约束的 manifest；**不生成官方升级容器或 E1089999.BIN**。本次参数探针12个模型案例与当前布局见 [param-probe-verification.json](param-probe-verification.json)；[completion-gate-verification.json](completion-gate-verification.json)等旧验证JSON是对应提交时的历史快照。

本次探针在12种合成条件下核对原厂发送次数、ABI、返回值及单字节变化；整套测试数以当前回归命令结果为准。此前独立审查提出的问题已补充回归；两个私有源码变异版本分别删掉回复清理和地址匹配，均被像素比较拒绝。
