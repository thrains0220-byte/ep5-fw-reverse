# E-P5 代码空洞中的胶片模块候选

这是基于 OM-C 已定位并由本项目独立核对的 E-P5 空间候选继续实现的一步：**原厂 ART 调用 → 本项目跳板与色彩核心 → 原厂 JPEG 调用**已经在受限 CPU 指令模型中连通。它尚未形成相机升级包，不能刷入；模块是否在真实启动后可用、缓冲区是否符合假设仍待确认。

## 源码与参考材料

已实际下载两类材料：

- `external/om-c-firmware/`：公开标签 dbv0.4.0，提交 `9165af1a2cab36f42054b0028ffda723190355bf`，只有 README。
- 发布页实际的 [Source code (zip)](https://github.com/azqeurio/om-c-firmware/archive/refs/tags/dbv0.4.0.zip)：375 字节，SHA-256 `05560fa39474d97dd7ca933485acf2f95d1fa4e4ada8abab1f7ae7065985b11d`。直接解压仅有目录及 15 字节 README，不是完整补丁工程。
- `external/om-c-reference/`：已下载并校验的 Windows 程序包、静态提取的补丁配置及代码对象。没有执行该应用。

本次利用的是其可核对的 E-P5 基线/地址/布局事实；`firmware/ep5_art_entry.*`、构建器和验证器为本项目新写的源码，没有复制第三方光圈环 payload 或应用实现。详细来源核对见 [OM-C 检查记录](OM_C_DBV040_REVIEW.md)。

## 模块布局已经实际链接

本项目将原有 `film.c`、`lut.c`、一个 Warm Negative LUT 及新的 E-P5 原厂调用桥一起用本地 GCC 编译，链接在 `[0x7e128010,0x7e130000)` 候选区域。选择 `-Os -mno-am33`，保留 RGB16 计算精度；主机参考和目标结果仍须逐字节相等。

| 部分 | CPU 地址 | 大小 |
| --- | --- | --- |
| 跳板、适配及实际色彩指令 | `0x7e128010` | 1,615 字节 |
| 对齐 | `0x7e12865f` | 1 字节 |
| 只读资格控制记录 | `0x7e128660` | 24 字节 |
| 单个 RGB16 LUT | `0x7e128678` | 29,478 字节 |
| 模型取指尾部填充 | `0x7e12f99e` | 8 字节 |
| 结束 / 区域剩余 | `0x7e12f9a6` | 剩余 1,626 字节 |

总长 **31,126 字节**，SHA-256 `3b7da973f74970d4e3de8dd9f2a2bf03b9227543ba110905d5247005994363f8`。链接脚本拒绝溢出、意外可写 data/BSS 和不符尺寸的 LUT；验证器核对普通 MN103 与 AM33 解码一致、实际表字节和默认控制值。

这比之前用测试调用者估算体积更具体，但仍只是一个固定地址的布局候选。没有证明整个 FF 区域在启动/拍摄期间不被其他任务或硬件使用，也未与 OM-C 的光圈环 payload 合并：两者会占用同一位置，不能叠加。

## 原厂调用与新代码怎样衔接

验证器核对原版主程序 SHA 和原始 `0x7e3ed8d1: cd b3 6f f0 10`，然后**只在模型的内存映像**中将该 5 字节调用换成 `dc 3f a7 d3 ff`，即跳入模块。原始 `rec_art_make_prim` 构造器、图像地址/几何 getter 都继续执行原版指令。

`ep5_art_entry.S` 保存全部八个通用寄存器和 MDR，预留 GCC 所需返回槽及 8 字节寄存器参数回写区，调用本项目 C 适配器，然后恢复寄存器/栈。最后重新发出原厂 JPEG 调用 `[d2,d3,a2,a3],16`，回到原厂 `0x7e3ed8d6` 继续执行。

CPU 模型在原始调用点、跳板重新调用前及 JPEG 入口观察参数/寄存器/栈。原生 CALL 本身会将返回地址写入 MDR，所以核对规则是：跳板发出 CALL **之前**恢复原 MDR，JPEG 入口 MDR 为跳板 CALL 的新返回地址。不能错误要求两个时刻的 MDR 都等于原始调用点值。

本次模型没有以主机算法代替像素处理；原厂构造、跳板、适配器、LUT/颜色计算全部执行目标指令。仅 REC 日志和 JPEG 编码本体是明确列出的服务模型。编码模型核对原始参数不变，并返回标记 `0x1234`，最终核对原始调用者正确收到该标记。

## 默认关闭与缓冲区资格

24 字节控制记录为六个小端 u32：tag、enabled、map_start、map_bytes、encoding、amount。构建器只生成 `tag=0x43355045`、其余为 0 的关闭记录，没有启用实机处理的命令行开关。

模型为各案例在内存中提供合成资格记录后才允许处理。当前适配器只处理已独立限定映射中的图像，拒绝：

- 无效 tag/启用值、空映射、地址范围回绕、容量不足。
- 映射覆盖模块或原始 JPEG 请求结构。
- 几何前后两对宽高不一致、奇数宽度或 native resize 选项。
- 未知编码或超出 0..256 的强度。

当前候选只显式假设 Y0/Cb/Y1/Cr、BT.601 全范围，且几何两对一致。没有把该假设视为真实 E-P5 色彩/步长契约。对于未知情况，色彩适配器不修改图像，跳板保留原厂编码调用。

这里没有接入看门狗/协作调度，也没有完成同一图像重复处理的策略；同步测试路径不给处理核心提供取消回调，因此不会产生“改到一半后取消仍继续编码”的状态。真实帧可能处理很久，不能据此开启机身处理。

## 验证和复现

15 个模型案例覆盖关闭、恒等、Warm Negative、半强度及上述非法条件。变色案例与主机 C 核心逐字节一致，非法条件固定要求原图字节不变；邻接保护字节、原始请求、通用寄存器、MDR、栈、编码调用次数及返回值均核对。

```bash
python3 tools/cave_entry.py data/ep5-decoded/00_0100_402c0020.decoded.bin \
  --out build/ep5-cave-module
python3 tools/cave_entry.py data/ep5-decoded/00_0100_402c0020.decoded.bin \
  --check --out generated/cave-entry-check.json
python3 -m unittest discover -s tests -v
```

输出目录/报告必须尚不存在。构建器生成 `film.elf`、原始模块 `film.bin`、反汇编及 `manifest.json`；没有修改并输出官方升级容器，没有生成 `E1089999.BIN`。`installable` 明确为 false。模型检查使用原始主程序，只允许模型栈和有界合成图像写入。

这一步减少了“能否装入候选空间、能否按原厂 ABI 衔接已有色彩核心”的未知项。后续仍需查清真实图像生产与生命周期、格式与色彩空间、启动驻留、缓存/调度、普通拍摄进入路径、重复处理及机内选择，最后才构建并实测实际固件。

后续[生产者检查](NATIVE_CONTRACTS.md)已执行启动读取参数、全尺寸申请/几何生成及中性滤镜列表构造，补上了读取请求覆盖模块候选的证据。实际 flash 读取、运行期不被覆盖和完整显影未验证，不能因此开启控制记录。
