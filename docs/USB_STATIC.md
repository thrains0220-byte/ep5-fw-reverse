# E-P5 1.8：USB 照片传输接口能证明什么

官方主程序的 MTP 模式公告 20 个操作。逐条读取注册指令得到同样的 20 项，能对应到设备信息、对象、属性等处理函数。没有一项能认定为任意内存读取或 USB 命令行。其他模式里有厂商版本查询，也有固件升级入口。本页没有向相机发送命令；它不证明在用固件与官方原版相同，也不证明升级或恢复可行。

**可复核的输入。** 对官方 E-P5 1.8 解包得到的 MAIN 运行：

```console
python tools/inspect_usb_static.py data/ep5-decoded/00_0100_402c0020.decoded.bin
```

[脚本](../tools/inspect_usb_static.py)核对 SHA-256 `dfe255e4d5a43329712c1fdfd6861ee1f3ef54a268b6096628bf045d8cc590df`。它从指令里的立即数读取表长、指针、注册操作和回调，并检查 MTP 公告与注册集合相同。以下地址均为 E-P5 此版本的 CPU 地址（MAIN 基址 `0x7e101020`）。

| 原厂代码 | 依据 |
| --- | --- |
| 模式选择及注册 | `0x7ee81798` 读取模式字节。模式 4 在 `0x7ee817b8` 调用 `0x7ee81d7d`。后者从 `0x7ee81d82` 起登记各操作；其中标准 GetDeviceInfo（0x1001）的回调是 `0x7ee8b8ec`。注册器 `0x7ee86db6` 将 16 位操作码放入节点开头、回调地址放入节点 +8。分派端 `0x7ee87180` 按操作码查表，通过会话条件后取节点 +8，在 `0x7ee871b3` 间接调用。 |
| 同一 VID/PID 对应两个模式 | `0x7ee819eb` 的设置函数中，模式 1 和 4 分别在 `0x7ee81a15`、`0x7ee81a27` 选取相同的 PID `012f`，但写到 `0xa0807796` 的内部模式不同。`0x7ee81a45…0x7ee81a5f` 依次写入 VID 的 `b4 07` 及 PID 两字节。模式 1 返回 18 个操作，无 MTP 的四个 98xx；模式 4 返回上表所述 20 项。因此识别到 `07b4:012f` 本身不能识别出模式 4。 |
| GetDeviceInfo 应答 | 回调经 `0x7ee81759` 取得模式。模式 4 的 VendorExtensionID 字段写入 6；在 `0x7ee8b967` 调用支持操作列表选择器 `0x7ee8d54f`，随后写 32 位数目及逐个 16 位操作码。在 `0x7ee8b99e`、`0x7ee8b9d5` 分别选择随后两个数组：事件、设备属性。 |
| 为什么 WPD 显示固件版本 1.00 | 官方 **1.8** 的 GetDeviceInfo 在 `0x7ee8ba77` 取 ROM 常量 `OLYMPUS` 填制造商，`0x7ee8ba86` 调型号 helper；`0x7ee8ba8f`（`fc dd ac 3b ee 7e`）取 ROM `0x7eee3bac` 的 ASCII **1.00**，在 `0x7ee8ba95` 调同一个 PTP 字符串编码器填 DeviceVersion；最后在 `0x7ee8ba9e` 调序列号 helper。DeviceVersion 字段是固定字符串，不读取机身升级版本；实机 WPD 属性显示 1.00 与菜单显示 1.8 不冲突。 |
| 设备属性 | 模式 4 的设备属性表位于 `0x7eee3e6e`，5 项：`5001 5011 d405 d406 d407`。标准 GetDevicePropValue 回调 `0x7ee8c71b` 对属性号 `(id & 0xfc00) == 0xd400` 分流到 `0x7ee83949`，该函数区分 `d405` 与经属性表查询的其他值。这里传入的是属性标识，不是主机指定的内存地址；未把这些字段解释成 ISP 或拍照任务状态。 |

模式 4 的列表在 `0x7eee3d8c`，按设备信息应答顺序为：

```text
1001 1002 1003 1004 1005 1006 1007 1008 1009 100a
100b 100f 1014 1015 1016 101b 9801 9802 9803 9805
```

最后四个是查询对象支持的属性、属性描述、属性值、属性列表。0x101b 是按对象句柄取文件片段；回调 `0x7ee8cac1` 引用原厂 GetPartialObject 错误日志。同一公告里还包括删除对象、格式化存储和设置属性，不能把整个列表当成只读操作清单。[标准操作码名称参考：Android 的 MTP 实现](https://android.googlesource.com/platform/frameworks/base/+/b6451228526288b158c3b0bf0c5abbd5b072d51c/media/mtp/mtp.h)

**不同模式的厂商入口。** 模式 0/5 在 `0x7eee3d52` 公告 29 项；模式 6 在 `0x7eee3dee` 公告 33 项。其 0x91xx 与模式 4 的 MTP 属性查询不同。例子是根据注册回调和回调内的原厂日志交叉识别的：

| 代码 | 回调 | 可确认的行为 |
| --- | --- | --- |
| `911c` | `0x7ee8a49b` | 引用 GetFirmwareUpdateMode 日志；该短函数在日志调用后把常数 1 和成功状态填进回复结构，没有读取主机给定地址。不能用它判定闪存状态或备份能力。 |
| `9120`、`9124` | `0x7ee8a54c`、`0x7ee8a5c1` | 分别引用 GetVersions、GetLanguageCode 日志。前者汇集四个内部调用的结果，后者按请求参数分支；未证明所有子调用无副作用。这两项不在模式 4 的公告中。 |
| `9123`、`9117` | 均为 `0x7ee8a894` | 注册处 `0x7ee81d02…0x7ee81d21` 两次复用同一函数地址；它引用 UpdateInitiate 日志。不能把相邻的厂商代码当作查询来试发。 |

**结论的边界。** 分派器未在注册表命中时，还会在 `0x7ee871d8` 检查操作码高位：某些 `0x9xxx` 请求可进入后备处理 `0x7ee872dd`，由内部服务决定是否接管。未验证该服务接受的全部请求；列表缺项不能证明不存在隐藏命令。目前没有从这个入口连到读取指定 RAM、执行命令、获得运行时 shell 或回刷救援的证据。USB VID/PID、Windows 能浏览照片、Wi-Fi 工程入口，以及其他机型的地址都不能补上这一段。

要判断真机是否处在这里的模式 4，可把**实际标准 GetDeviceInfo 应答**中的 VendorExtensionID、操作列表及属性表与以上数字对照。Windows 高层 WPD 的能力清单不一定是原始应答；仅有该清单时，结论应写为“与 MTP 相符，未逐项核对”。

本轮 Windows 只读会话识别出 E-P5、OLYMPUS、协议 MTP: 1.00，并可枚举照片对象。WPD 查询厂商操作清单和扩展描述时返回 `0x80070005`（Access denied）；这不是相机返回 PTP OperationNotSupported。没有放宽访问权限或发送原始 GetDeviceInfo；不能用该拒绝推定真机端的操作清单。
